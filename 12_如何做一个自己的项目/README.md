# 第十二章：如何做一个自己的项目 —— 个人开发者与应届生的 AI 项目方法

前面的章节已经介绍了开发环境、工作流、Agent、LangChain、LangGraph 和 RAG。到了这一章，重点从“学会一种技术”转向“把几种技术组织成一个能说明价值、能够运行、经得住追问的项目”。

个人项目常见的难点并不在于少写了几个功能，而在于项目从哪里开始、为谁解决问题，以及如何证明它确实有用。实践中尤其容易遇到下面四类问题：

1. **一开始就从零搭建所有模块**：没有先评估成熟的开源项目，也没有核对 GPL、AGPL 等许可证对分发、商用和开放源码的要求；
2. **为了使用 AI 而改造业务**：忽视了原有 Web、小程序或管理系统已经形成的流程，新增功能与真实任务脱节；
3. **有演示页面，却缺少真实反馈**：数据过于理想，异常情况没有覆盖，项目只能完成预设问答，无法说明在真实场景中是否可靠；
4. **简历只写接入了某个模型**：没有交代技术选择、成本、失败案例、测试条件和迭代过程，面试官很难据此判断工程能力。

本章从开源选型、已有业务改造、数据反馈和求职表达四个角度展开。每一节都把项目目标落实到具体问题、实现选择和验收证据，帮助读者做出能够持续修改、说明并复现的 AI 项目。

> 无论项目用于独立产品、课程练习还是求职展示，都应先明确一个真实问题，再说明技术为什么适合这个问题。运行速度、成本和准确率只有写清测试条件才有意义；架构图也要能对应到实际代码与数据流。

## 从项目想法走到可验证结果

项目不必一开始就追求完整平台。先写清目标用户、一个高频任务、现有做法和可量化的改进，再决定是改造开源项目、接入已有业务，还是从小型原型开始。

每个阶段至少留下三类证据：能够复现的运行方式、覆盖正常与异常情况的测试记录、一次真实或脱敏试用得到的反馈。简历中只写已经验证的范围，性能、成本和准确率都注明测试条件。

使用开源代码、模型权重和公开数据时，分别核对许可证和使用条件。二次开发节省的是基础建设时间，不会自动解决升级、数据和合规问题。
