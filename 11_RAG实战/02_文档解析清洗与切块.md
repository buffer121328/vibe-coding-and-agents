# 11.2 数据源又脏又乱怎么办？—— 文档解析、清洗与切块

> **痛点场景**：你拿到手的不是干净的文档，而是一堆“车祸现场”——扫描版的 PDF 双栏错乱、Word 里镶着表格、网页导出带一堆广告、还有页眉页脚和“机密勿外传”的水印反复出现。如果直接把这些脏数据塞进向量库，结果就是：**你喂给系统的每一份垃圾，最后都会变成用户收到的垃圾答案。**  
> 本节我们用「痛点 → 思路 → 代码实现 → 拓展」四段式，把“数据准备层”彻底打通。

---

## 🩹 痛点：垃圾进，垃圾出（Garbage In, Garbage Out）

先看一组真实的“车祸现场”：

| 数据源形态 | 典型脏点 | 后果 |
| :--- | :--- | :--- |
| 扫描 PDF | 缺字、乱码、双栏混读、需要 OCR | 检索到一堆“乱码碎片”，完全没法用 |
| 带表格的 Word/Excel | 表格被拆行、表头丢失 | 大模型看错列，答错数据 |
| 网页导出的 HTML | 导航、广告、版权声明混入正文 | 语义向量被噪声稀释 |
| 内部旧文档 | 页眉页脚、“第 38 页”、水印 | 相同噪声反复入库，污染检索结果 |

**为什么解析这一步决定了整个 RAG 的上限？** 因为后面所有环节（切块、嵌入、检索、生成）都是在“已解析出的文本”上进行的。这一步出错，后面再高级的技术也救不回来。

---

## 💡 思路：三步走，把“脏数据”变成“干净 Chunk”

**第 1 步：解析（Parsing）**—— 把二进制文件变成文字。核心是“按格式选对工具”：

| 文件格式 | 轻量方案 | 重量级/高保真方案 |
| :--- | :--- | :--- |
| PDF | `pypdf`、`pymupdf`(fitz) | [MinerU](https://github.com/opendatalab/MinerU)、[Marker](https://github.com/VikParuchuri/marker)（还原公式/多栏/表格为 Markdown） |
| Word | `python-docx`、`docx2txt` | [Unstructured](https://github.com/Unstructured-IO/unstructured)（统一几十种格式） |
| HTML | `BeautifulSoup` | `unstructured` 的 `partition_html` |
| Markdown | 直接读文本 | `MarkdownHeaderTextSplitter` 保留标题层级 |

**第 2 步：清洗（Cleaning）**—— 去掉噪音、归一化文本。常见的清洗操作：
- 删除页眉页脚/水印（“第 38 页”、“机密文件严禁外传”）；
- 归一化空白（多个空格、`\n` 混乱、全角半角不统一）；
- 去掉 HTML 标签、脚本、导航广告；
- 把表格按“行 × 列”转成可读的文本段落（保留表头语义）。

**第 3 步：切块（Chunking）**—— 把长文裁成适合检索与喂给 LLM 的小块，并挂上元数据。这一步决定了“检索精度”和“上下文完整性”的平衡。

为了让代码贴近现实，我们构造一批“带病”文档来演练：一份带页眉页脚和双栏混排的 PDF 提取文本、一段带 HTML 标签的网页内容、一份结构化的 Markdown 规章。

## 🧑‍💻 代码实现：从“脏文件”到“干净 Chunk”的完整管道

> 下面的代码直接复用了 LangChain 生态，但在三处做了比“默认用法”更工程化的处理：**按后缀自动选解析器**、**正则清洗去噪**、**切块时统计质量并注入元数据**。

```python
# 11.2 数据准备管道：解析 → 清洗 → 切块 → 元数据
import re
from pathlib import Path
from typing import List

from langchain_core.documents import Document
from langchain_text_splitters import RecursiveCharacterTextSplitter

# ============ 1. 解析：按文件后缀自动选择解析器 ============
def load_text_by_ext(path: Path) -> str:
    """返回统一格式的纯文本。生产环境可按需替换为 MinerU/Unstructured 等高保真解析器。"""
    suffix = path.suffix.lower()
    if suffix in {".md", ".txt"}:
        return path.read_text(encoding="utf-8")
    if suffix == ".html":
        # 用正则粗略剥掉标签，严谨场景建议 BeautifulSoup + 白名单
        html = path.read_text(encoding="utf-8")
        return re.sub(r"<[^>]+>", "", html)
    # 生产环境：.pdf 用 pymupdf/MinerU，.docx 用 python-docx
    raise NotImplementedError(f"暂未实现 {suffix} 的解析器")

# ============ 2. 清洗：去噪 + 归一化 ============
NOISE_PATTERNS = [
    r"第\s*\d+\s*页",            # 页眉页脚："第 38 页"
    r"机密文件[，,]?严禁外传",      # 水印/免责声明
    r"\bPage\s+\d+\b",            # 英文分页
    r"^\s*[-–—]\s*\d+\s*[-–—]\s*$",  # 单独成行的页码
]

def clean_text(raw: str) -> str:
    text = raw
    for pat in NOISE_PATTERNS:
        text = re.sub(pat, "", text)
    # 归一化空白：多个空格/换行压成一个空格
    text = re.sub(r"[ \t]+", " ", text)
    text = re.sub(r"\n{3,}", "\n\n", text)
    # 全角空格等不可见字符
    text = text.replace("\u3000", " ")
    return text.strip()

# ============ 3. 切块：递归字符切块（中文场景） ============
def make_splitter(chunk_size: int = 400, overlap: int = 60) -> RecursiveCharacterTextSplitter:
    """中文文档建议把 '。！？；' 加进分隔符，优先在句边界下刀，避免腰斩句子。"""
    return RecursiveCharacterTextSplitter(
        chunk_size=chunk_size,
        chunk_overlap=overlap,
        separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],
        length_function=len,
    )

# ============ 4. 组装完整管道 ============
def build_chunks(path: Path, source_name: str, category: str) -> List[Document]:
    raw = load_text_by_ext(path)
    cleaned = clean_text(raw)
    splitter = make_splitter()
    chunks = splitter.split_text(cleaned)
    return [
        Document(
            page_content=chunk,
            metadata={"source": source_name, "category": category, "chunk_index": i, "total": len(chunks)},
        )
        for i, chunk in enumerate(chunks)
    ]

# ============ 5. 运行验证 ============
if __name__ == "__main__":
    demo_doc = Path("demo.md")
    demo_doc.write_text(
        "第 1 页\n"
        "【员工差旅管理制度】\n"
        "第一条 本制度适用于全体正式员工。\n"
        "第二条 一线城市住宿标准为每人每天不超过 500 元；二线城市不超过 350 元。\n"
        "第三条 出差餐饮补贴为每人每天 150 元，无需发票。\n"
        "机密文件，严禁外传\n"
        "第 2 页\n"
        "第四条 差旅报销单须在返回工作地后 5 个工作日内提交 OA 系统。\n",
        encoding="utf-8",
    )

    docs = build_chunks(demo_doc, "差旅制度_2026.md", "行政")
    print(f"共生成 {len(docs)} 个 Chunk")
    for d in docs:
        print(f"\n[chunk {d.metadata['chunk_index']}/{d.metadata['total']}] source={d.metadata['source']}")
        print(d.page_content)
```

**这段代码与“随手一写”的 Demo 最大的不同**在于：
1. **清洗是显式的一步**，而不是直接拿脏文本切块；
2. **元数据注入**了 `source / category / chunk_index`，为后面 11.5 的元数据过滤检索（只搜某个分类）和 11.9 的评估归因铺路；
3. **分隔符针对中文定制**，优先在句号、问号、分号处下刀。

## 🎯 进阶：四种切块策略怎么选？

| 切块策略 | 原理一句话 | 适合场景 | 优缺点 |
| :--- | :--- | :--- | :--- |
| **递归字符切块** | 按分隔符优先级逐级下刀 | 通用基线 | 简单快，但无结构意识 |
| **标题层级切块** | 按 `#/##/###` 切，并把标题写进元数据 | 规范的技术文档、Wiki | 保留文档结构，上下文不丢 |
| **语义切块** | 用 Embedding 判断相邻句子的相似度，拐点处切块 | 叙事散文、话题漂移多的长文 | 块更“懂意思”，但要多次调用 Embedding |
| **父子切块** | 小块用于精准匹配，命中后取回完整大块 | 合同、研报、技术白皮书 | 精度与上下文兼得，但要多存一层文档库 |

### 父子切块（ParentDocumentRetriever）代码要点

它的核心思想是：**“用小个子去撞门（向量比对），撞开后把一家子大个子请进来（喂完整父文档给 LLM）。”**

```python
from langchain.retrievers import ParentDocumentRetriever
from langchain.storage import InMemoryStore
from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings
from langchain_text_splitters import RecursiveCharacterTextSplitter

# 父切块：保完整段落；子切块：负责高敏度命中
parent_splitter = RecursiveCharacterTextSplitter(chunk_size=800, chunk_overlap=80)
child_splitter = RecursiveCharacterTextSplitter(chunk_size=160, chunk_overlap=20)

# 向量库只存子块向量；docstore 单独存完整父文档
vectorstore = Chroma(collection_name="parent_demo", embedding_function=OpenAIEmbeddings())
docstore = InMemoryStore()   # 生产可换 Redis/SQLite，避免重启丢数据

retriever = ParentDocumentRetriever(
    vectorstore=vectorstore,
    docstore=docstore,
    child_splitter=child_splitter,
    parent_splitter=parent_splitter,
)
# retriever.add_documents(documents)  # 自动在底层建立父子映射并入库
```

## 🚀 拓展：切块质量的“体检报告”

切块好不好，不能靠感觉，建议在管道里顺手输出一份“体检报告”：

| 体检项 | 判定标准 | 说明 |
| :--- | :--- | :--- |
| **块大小分布** | 最大值/最小值/均值是否远离设定值 | 若大量块“顶格”说明有内容被硬切 |
| **句尾完整率** | 以句号/问号结尾的块占比 | 越高越好，说明没腰斩句子 |
| **标题丢失率** | 无任何标题元数据的块占比 | 对标题切块很重要 |
| **重复率** | 块与块的重叠文本占比 | overlap 设置过大会造成信息冗余 |

## 🌊 深水区：真实世界的文档没有这么“乖”

上面的管道处理的是“理想脏文档”。但企业里真正让人头秃的是这几类“深水区选手”：

| 深水区形态 | 难在哪 | 普通解析器的下场 |
| :--- | :--- | :--- |
| **几百页的扫描件 PDF** | 文字是“图片”不是文本，必须 OCR | `pypdf` 提出来是空字符串 |
| **财务报表 / 实验数据表** | 合并单元格、跨页表格、多层表头 | 表格被拆成一行行“散装文本”，列语义全丢 |
| **论文 / 理工文档** | LaTeX 公式、上下标、脚注 | 公式变成乱码，检索“E=mc²”永远命中不了 |
| **图文混排的产品手册** | 截图里藏着关键步骤文字 | 图片被直接丢弃，正好漏掉用户最需要的部分 |

**生活化比喻**：轻量解析器像一个只认识铅字印刷的图书管理员——印刷体它读得飞快，但你递给它一份手写病历和一张 X 光片，它就两眼一抹黑。深水区需要的是“会看片子、能认潦草字、还懂表格”的高级专家。

### 现代高保真解析器：MinerU 与 Docling

新一代文档解析器把「版面分析 + OCR + 表格识别 + 公式还原」打包成一条流水线，直接输出结构干净的 Markdown/JSON：

| 解析器 | 出品方 | 拿手绝活 | 一句话定位 |
| :--- | :--- | :--- | :--- |
| [MinerU](https://github.com/opendatalab/MinerU) | 上海 AI 实验室 OpenDataLab | 公式转 LaTeX、表格转 HTML/Markdown、阅读顺序还原 | 学术与中文场景的高保真之王 |
| [Docling](https://github.com/docling-project/docling) | IBM | 表格结构还原、图文混排理解、与 LlamaIndex/LangChain 原生集成 | 企业文档的“瑞士军刀” |

> 💡 **选型直觉**：文档以论文、研报、公式多 → 选 MinerU；文档以 Word/Excel/PPT 混合、要接框架管道 → 选 Docling。两者都支持本地部署，涉密数据不出内网。

用 Docling 把一份带表格的 PDF 一步变成“RAG 友好”的 Markdown：

```python
# pip install docling
from docling.document_converter import DocumentConverter

converter = DocumentConverter()
result = converter.convert("财报_2025.pdf")

# 导出为 Markdown：表格自动还原成 | a | b | 格式，标题保留层级
md = result.document.export_to_markdown()
print(md[:500])

# 也可以拿结构化 JSON：每个表格、每张图片、每个标题都是独立节点
for table in result.document.tables:
    df = table.export_to_dataframe()   # 直接得到 pandas DataFrame
    print(df.head())
```

### 表格、公式、图文混排的入库策略

解析出来之后，**不同形态的信息要走不同的入库通道**，不能用一把尺子切：

| 信息形态 | 推荐策略 | 为什么 |
| :--- | :--- | :--- |
| **表格** | 每张表独立成块，表头 + 摘要行写成自然语言一并嵌入；不跨表切块 | 切开表格 = 拆散一家人，检索命中一半永远答不全 |
| **公式** | 保留 LaTeX 原文入库，同时补一句“人话翻译” | 向量模型对 LaTeX 符号不敏感，人话负责语义命中，LaTeX 负责精确还原 |
| **图片** | 用多模态模型生成图片描述（caption）与图片一起入库；或直接走 11.14 的多模态 RAG | 让“图片里的话”也能被文本检索命中 |
| **扫描件** | 先 OCR（MinerU/Docling 内置），按置信度抽样人工质检 | OCR 不是 100% 准，低置信度段落混进库里就是定时炸弹 |

**一句话总结**：数据层的深水区没有银弹，只有“按形态分流 + 高保真解析器打底 + 抽样质检兜底”的组合拳。

## 🧬 补全生产链路：来源、版本、去重与权限

只把文本切干净还不够。企业知识像办公室里流转的合同：你必须知道它从哪来、哪天生效、谁能看、是否已经被新版替代。否则检索器可能把“2025 年住宿上限 450 元”和“2026 年住宿上限 500 元”一起交给模型，模型只能猜。

每个 Chunk 至少保留这些元数据：

| 字段 | 解决的问题 | 示例 |
| :--- | :--- | :--- |
| `source_id` / `source_uri` | 能否追到原文件 | `TRAVEL-2026-07#p2` |
| `source_hash` / `chunk_id` | 内容是否变化、写入能否幂等 | `sha256:...:chunk-3` |
| `effective_from/to` | 新旧制度冲突时选谁 | `2026-07-01` |
| `status` | 草稿、现行、废止、隔离 | `active` |
| `tenant` / `acl` | 谁能检索到 | `tenant=acme, acl=employee` |
| `parser_version` / `embedding_version` | 哪个处理批次产生 | `docling-2.x / embed-v3` |
| `page` / `bbox` | 引用如何跳回原文 | `page=2, bbox=[...]` |

### 去重不能只看文件名

同一制度可能同时出现在邮件附件、网盘和 Wiki。文件名不同，但内容几乎一样。三份重复内容进入 Top-K 会制造“多数票错觉”，也会挤走真正不同的证据。

1. **完全重复**：对规范化正文做内容哈希，哈希相同只留一份；
2. **近重复**：用 MinHash、SimHash 或向量相似度识别轻微改名、换页眉的副本；
3. **版本关系**：相似不代表重复。新旧制度要保留谱系，但默认检索只查 `active`，历史问题才显式查旧版；
4. **权威来源**：内部正式制度应压过论坛截图和网页转载，来源等级要进入排序或过滤。

### 切块好坏最终由“能不能回答”决定

句尾完整率只能做体检，不能证明检索效果。更可靠的办法是准备一批问题和相关 Chunk 标注，对不同切块配置做对照：

| 实验变量 | 观察指标 | 常见现象 |
| :--- | :--- | :--- |
| `chunk_size` / overlap | Recall@K、重复率、上下文 Token | 块太小缺背景，块太大语义被稀释 |
| 标题是否继承 | 精确命中率、无标题率 | 正文里的“第五条”脱离标题后含义不清 |
| 父子切块 | 子块 Recall、父块生成忠实度 | 找得准但回填过大，也会带来噪声 |
| 表格独立切块 | 数字题正确率 | 只命中某一行却丢表头，会把列含义答反 |

配套 `code/testdata/` 故意放入现行制度、废止旧版和不可信网页，外加 `真实RAG演示文档/` 四份标准案例（协作手册、差旅报销、设备故障、HR 制度）；`s02_data_pipeline.py` 为 Chunk 生成稳定 ID、状态与信任级别，并输出语料体检报告。`shared_corpus.py` 复用同一套解析口径把 8 份文档切成约 28 个页级 Chunk，后续各小节脚本的检索、评估与引用演示用的都是这份真实语料。
