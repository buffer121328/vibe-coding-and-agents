# 11.1 RAG 完整生命周期分层：先把整台机器拆开看

> **“与其给 RAG 贴满‘第一代、第二代、第三代’的进化标签，不如把它当成一条从原料到成品的流水线工厂 —— 我们逐层参观，看每一道工序在解决什么具体问题。”**  
> 本章采用一种与大多数教程不同的讲法：**先建立“整机”视野，再逐个攻破业务痛点**。而建立整机视野的最好方式，就是把 RAG 按**完整生命周期**分成四大层次，像参观工厂一样一层层看过去。

---

## 💡 为什么不用“版本号”叙事？

很多资料会把 RAG 分成 Naive RAG（朴素版）→ Advanced RAG（进阶版）→ Agentic RAG（智能体版），像手机换代一样讲“第几代”。这种讲法有两个毛病：

1. **容易产生“一代更比一代强”的错觉**：实际上 Naive 的“简单切块 + 向量检索”在数据量小、问题简单时依然是最优解，你没必要为了“用上高级货”而强行加一堆组件；
2. **忽略了“组件之间的协作”**：真实生产系统里，HyDE、混合检索、重排、图谱、Agentic 自省是**同时并存、各司其职**的，而不是“换代淘汰”的关系。

所以我们换一种更贴近工程实践的切法 —— **按数据在系统中的流转阶段分层**。这也是你以后向别人讲清任何 RAG 系统时最好用的框架。

### ① 数据准备层（离线）：决定 RAG 的上限

这是整条链路里最“脏、累、但回报最高”的一层，业界有句俗话：**“垃圾进、垃圾出”（Garbage In, Garbage Out）**。这一层要回答的问题是：

| 子问题 | 典型做法 | 对应章节 |
| :--- | :--- | :--- |
| 原始文件五花八门，怎么统一成干净文本？ | PDF/Word/HTML/Markdown 多格式解析、去噪、OCR、表格还原 | [11.2](02_文档解析清洗与切块.md) |
| 拆成多大多小的块才不会语义断裂？ | 递归字符切块、标题切块、语义切块、父子切块 | [11.2](02_文档解析清洗与切块.md) |
| 怎么把文字变成机器能算的坐标？ | Embedding 模型（BGE/GTE/OpenAI）、多模态嵌入 | [11.3](03_向量嵌入与多模态.md) |
| 向量存哪里、怎么索引才查得快？ | 向量数据库（Chroma/Qdrant/Milvus/Pgvector）与 ANN 索引 | [11.4](04_向量库与ANN索引.md) |

> 💡 **比喻**：这一层就像餐厅的后厨 —— 买菜、洗菜、切菜、备料。主厨（LLM）手艺再高，端上来的如果是带着泥巴、切成碎渣的食材，也做不出好菜。

### ② 检索层（在线）：决定 RAG 的精度

用户问一个问题，系统要在几十毫秒内从海量数据里捞出最相关的几段。这一层要回答：

| 子问题 | 典型做法 | 对应章节 |
| :--- | :--- | :--- |
| 用户口语化、有指代、意图模糊怎么办？ | 查询重写（HyDE / Multi-Query / Step-Back）、意图路由 | [11.6](06_查询重写与意图路由.md) |
| 向量检索“意会”失灵，关键词检索“抠字眼”失灵怎么办？ | 混合检索：Dense + BM25 多路召回 | [11.5](05_混合检索与重排.md) |
| 多路结果怎么科学合并排序？ | RRF 倒数排名融合 + Cross-Encoder 重排 | [11.5](05_混合检索与重排.md) |
| 宏观/跨章节问题单靠向量搜不到怎么办？ | 知识图谱与 GraphRAG 的社区级检索 | [11.7](07_知识图谱与GraphRAG.md) |

### ③ 生成层（在线）：决定 RAG 的质感

检索回来的“食材”再好，也要主厨（LLM）把它们组织成一道完整的菜。这一层要回答：
- 检索回来的 Top-K 段落怎么拼进 Prompt？顺序、去重、压缩噪声；
- 怎么让大模型“只根据资料说话”而不是自由发挥（降低幻觉）；
- 怎么让回答自带引用出处（溯源），方便用户和系统核查。

### ④ 评估与运维层（闭环）：决定 RAG 能不能持续变好

这是最容易被人忽略、但生产环境最关键的一层。没有这一层，你永远说不清“我改了切块参数之后，系统到底是变好了还是变差了”。这一层要回答：
- 用什么量化指标衡量“检索准不准、回答忠不忠实”？（RAG 黄金三元组）
- 线上每一次请求的耗时、Token 消耗、节点链路怎么观测？（LangSmith / Phoenix）
- 出现 Badcase 后如何沉淀成回归集，防止下次改动把效果改回退？

## 🧭 RAG 与“邻居技术”的边界怎么划？

学习 RAG 时最常见的困惑是：它和微调、长上下文、Agent 到底什么关系？用一张表说清：

| 技术 | 核心思路 | 适合场景 | 不适合场景 |
| :--- | :--- | :--- | :--- |
| **RAG（本章主角）** | 动态检索外部资料喂给 LLM | 知识会频繁更新、需要溯源、数据量大 | 需要模型掌握某种“说话风格/推理习惯” |
| **模型微调（Fine-Tuning）** | 用数据改变模型权重 | 固定风格、领域行话、特定格式输出 | 知识更新快（微调一次成本高、周期长） |
| **长上下文（Long Context）** | 把更多资料直接塞进窗口 | 单篇/少量文档就能覆盖问题 | 资料海量（塞不下）、成本爆炸、容易“迷失在中间” |
| **Agent（智能体）** | 自主规划、调工具、多步推理 | 需要拆解多步任务、动态决策 | 单轮简单问答（用 Agent 反而更慢更贵） |

> 💡 **生产实践**：这几者从来不是“二选一”，而是**组合拳** —— 用微调定风格，用 RAG 供知识，用长上下文兜底单文档，用 Agent 编排复杂任务。

## 🎯 本章的“问题驱动”学习地图

现在你已经有了整机视野，接下来 8 个小节就是**沿着这条流水线，一站一站去解决真实痛点**：

1. **数据侧**：数据脏乱（11.2）→ 机器不懂语义（11.3）→ 数据多查不快（11.4）；
2. **检索与理解侧**：搜不准搜不全（11.5）→ 提问含糊（11.6）→ 宏观答不了（11.7）；
3. **智能与治理侧**：幻觉与答非所问（11.8）→ 无法度量（11.9）。

每一节都用统一的四段式结构：**「痛点 → 思路 → 代码实现 → 拓展」**，让你不仅知道“有这个东西”，还能亲手把它写出来。
