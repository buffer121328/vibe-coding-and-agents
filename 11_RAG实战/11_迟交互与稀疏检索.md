# 11.11 检索的下一档功率：迟交互、稀疏学习与多库调度

> **痛点场景**：你已经用上了 11.5 的“BM25 + 向量 + Cross-Encoder 重排”，但总有些场景卡在瓶颈上——长文档里**一句话的细微差别**被“一整段压成一个向量”抹平了；扫描件里的**关键截图**文本层压根没有；公司有产品库、制度库、工单库好几个知识库，**该问谁**全靠 if-else 硬编码。本节把检索层的“下一档功率”一次讲透：**迟交互（ColBERT/ColPali）、稀疏学习（SPLADE）、多知识库调度。**

---

## 🩹 痛点：一句话一向量，抹平了词级细节

11.3 讲的向量嵌入是“双塔”模型：把整段文字压成**一个**向量再比对。就像把一整部电影压成一张海报——大体风格能对上，但“主角在第 47 分钟说的那句话”早被压缩没了：

| 阵型 | 怎么比 | 强项 | 短板 |
| :--- | :--- | :--- | :--- |
| **双塔（Bi-Encoder）** | 段落→1 个向量，问题→1 个向量，算一次相似度 | 快，可离线建库，ANN 友好（11.4） | 词级细节被压缩抹平 |
| **交叉（Cross-Encoder）** | 问题+段落拼一起喂进模型，逐 token 交互打分 | 精度天花板最高（11.5 重排） | 每对都要跑一次模型，没法先建库 |
| **迟交互（Late Interaction）** | 段落**每个 token 一个向量**离线存好；查询时问题 token 与段落 token 逐对“晚点再交互” | 词级精度 + 离线建库两者兼得 | 向量数量暴涨几十倍，存储成本高 |

第三种“迟交互”就是 ColBERT 的核心思想：**把“压缩成一句话”变成“每人带一小队士兵入场”**——段落里的每个词都是一个携带完整上下文的向量，查询词和文档词之间可以两两配对找最强呼应（MaxSim），细粒度信息不再丢失。

## 🧑‍💻 代码实现一：手写 MaxSim，看穿迟交互的本质

> ColBERT 的打分公式其实只有一行：查询的每个 token，去文档所有 token 向量里找一个“最像的”（MaxSim），再对查询所有 token 求平均。我们用 numpy 手搓一遍：

```python
# 11.11 迟交互核心：手写 MaxSim
import numpy as np

def maxsim_score(query_vecs: np.ndarray, doc_vecs: np.ndarray) -> float:
    """query_vecs: (m, d) 查询 m 个 token 的向量
       doc_vecs:   (n, d) 文档 n 个 token 的向量
       每个查询 token 在文档里找最相似的文档 token，再平均。"""
    sim = query_vecs @ doc_vecs.T          # (m, n) 两两相似度
    return float(sim.max(axis=1).mean())   # 每行取最大 → 对查询求平均

# 假设已经用 ColBERT 模型拿到了 token 级向量（实际用 pylate/RAGatouille）
q = np.random.RandomState(0).randn(3, 8)     # 查询 3 个 token
doc_a = np.random.RandomState(1).randn(12, 8)  # 文档 A：12 个 token
doc_b = doc_a.copy()
doc_b[5] = q[0]   # 文档 B 在某个 token 上与查询“遥相呼应”

print(maxsim_score(q, doc_a))   # ≈ 0.10  泛泛之交
print(maxsim_score(q, doc_b))   # 更高     一个词的“神呼应”就能被捕捉到
```

**这就是迟交互的全部灵魂**：文档 B 只有一个 token 与查询呼应，双塔会把这点呼应稀释在平均里，而 MaxSim 让它“一票突出”。

生产中不必手搓，直接用封装库：

```python
# pip install pylate
from pylate import models, retrieve

colbert = models.ColBERT(model_name_or_path="lightonai/GTE-ModernColBERT-v1")
docs = ["员工差旅住宿标准：一线城市每晚 500 元。",
        "公司年会每年 12 月举办，全员参加。"]

# 离线：每个 token 一个向量，全部存进索引
docs_embeddings = colbert.encode(docs, is_query=False)

# 在线：查询 token 与文档 token 逐一 MaxSim
query_embeddings = colbert.encode("住一线城市一晚补贴多少？", is_query=True)
retriever = retrieve.ColBERT(docs_embeddings=docs_embeddings, documents_ids=["d1", "d2"])
rankings = retriever.retrieve(query_embeddings, k=2)
print(rankings[0][0])   # 命中差旅制度那条
```

## 🧑‍💻 代码实现二：SPLADE —— 会自己“扩词”的稀疏检索

BM25 是“抠字眼”的老实人：你搜“手提电脑”，它绝不会想到“笔记本电脑”。SPLADE 的思路很聪明：**仍然输出稀疏向量（兼容倒排索引，11.4 的基础设施照用），但稀疏向量的每个维度权重由模型学会“智能扩词”**——相当于一个既懂倒排索引又懂语义的混血儿。

```python
# pip install sentence-transformers
from sentence_transformers import SparseEncoder

splade = SparseEncoder("naver/splade-cocondenser-ensembledistil")

docs = ["员工差旅住宿标准：一线城市每晚 500 元。",
        "公司年会每年 12 月举办，全员参加。"]
doc_embeds = splade.encode(docs)

# 稀疏向量：绝大多数维度是 0，只有少数“词”维度有权重
query_embed = splade.encode_query("住一线城市一晚补贴多少？")
scores = splade.similarity(query_embed, doc_embeds)
print(scores)   # “补贴”命中了文档里的“标准”类似语义——BM25 做不到
```

| 对比项 | BM25 | SPLADE | Dense 双塔 |
| :--- | :--- | :--- | :--- |
| 会扩词/近义 | ❌ | ✅ 模型学的 | ✅ |
| 术语精确匹配（型号/编号） | ✅ 强 | ✅ 强 | ⚠️ 常糊 |
| 索引基础设施 | 倒排索引 | 倒排索引 | 向量索引 |
| 存储成本 | 低 | 中 | 中 |

> 💡 **选型直觉**：企业检索里满是“型号、条款号、错误码”这类必须抠字眼的词，SPLADE 是 BM25 的“无痛升级”——索引结构不变，只把“词的权重”换成模型算的。

## 🧑‍💻 代码实现三：多知识库调度 —— 给问题装一个“分诊台”

11.6 的意图路由解决“把问题翻译清楚”，本节解决“**翻译清楚之后该进哪个库**”。核心是：轻量分类器先分诊，**低置信度就走全库兜底**，宁可慢一点也不能答错门：

```python
# 11.11 多知识库调度：语义分诊 + 置信度兜底
from pydantic import BaseModel, Field
from langchain_core.prompts import ChatPromptTemplate
from langchain_openai import ChatOpenAI

class Triage(BaseModel):
    """分诊结果：去哪个知识库、置信度多少"""
    kb: str = Field(description="目标知识库：product / policy / ticket / unknown")
    confidence: float = Field(description="0~1 的置信度")
    reason: str = Field(description="一句话理由")

triage_llm = ChatOpenAI(model="gpt-4o-mini", temperature=0).with_structured_output(Triage)

ROUTER_PROMPT = ChatPromptTemplate.from_template(
    "你是知识库分诊台。可用知识库：\n"
    "- product：产品功能、参数、价格\n"
    "- policy：公司制度、报销、考勤\n"
    "- ticket：历史工单、故障案例\n"
    "用户问题：{question}\n输出目标库与置信度。拿不准就输出 unknown。"
)

def route(question: str, retrievers: dict, threshold: float = 0.7) -> list:
    r = triage_llm.invoke(ROUTER_PROMPT.format(question=question))
    if r.kb != "unknown" and r.confidence >= threshold:
        return retrievers[r.kb].invoke(question)        # 高置信：直奔对应库
    # 低置信兜底：并发查所有库，交给 11.5 的 RRF/重排统一裁决
    all_hits = []
    for kb, ret in retrievers.items():
        all_hits.extend(ret.invoke(question))
    return all_hits
```

**调度层的三个工程要点**：

1. **置信度阈值要靠 11.9 的评测集调**，不是拍脑袋；误路由一次，用户收到的是驴唇不对马嘴的答案；
2. **兜底永远要有**：分类器再准也有翻车的时候，全库并发 + 重排是保命的“全科会诊”；
3. **路由结果要写进 Trace（11.9）**：上线后看“unknown 率”和“路由命中率”，unknown 率飙升往往意味着新话题出现了，该建新库或补训练样本了。

## 🚀 拓展：迟交互很香，但账要先算清

| 维度 | 双塔 | 迟交互（ColBERT） | 什么时候上 |
| :--- | :--- | :--- | :--- |
| 存储 | 1 文档 = 1 向量 | 1 文档 = 几十~几百个 token 向量（约为双塔的 100 倍+，可用 ColBERTv2 压缩到 ~1/10） | 文档量百万级以下可接受 |
| 检索延迟 | ANN 一次 | 需要专门索引（PLAID），工程复杂度更高 | 有专门基础设施再上 |
| 精度收益 | 基线 | 对长文档、细粒度匹配提升明显 | 先用 11.9 评测集验证“值得”再迁 |

> 💡 **务实的升级路径**：先用 11.5 的混合检索打地基 → 拿 11.9 的评测集证明瓶颈在“词级匹配” → 再把重排层换成迟交互（成本可控）→ 最后考虑把召回层也换成 SPLADE/ColBERT。**别为了新而新，先证明旧刀不够快。**
