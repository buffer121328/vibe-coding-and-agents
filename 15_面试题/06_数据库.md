# 15.6 数据库

> 本节整理 35 道数据库面试题，覆盖关系型数据库、索引、事务、并发、缓存、分片、迁移，以及 Agent 的会话、记忆和向量检索场景。回答数据库问题时，最好同时说明一致性、性能、容量和恢复成本。

## 一、关系模型与索引

### 1. 关系型数据库和 NoSQL 数据库怎么选？

**面试问法**：什么场景适合 MySQL 或 PostgreSQL，什么场景适合 NoSQL？

**参考答案**：关系型数据库提供结构化 schema、事务、关联查询和成熟的约束，适合订单、账户、权限和需要强一致性的业务。NoSQL 包括键值、文档、列族和图数据库，通常在灵活 schema、水平扩展或特定访问模式上更有优势，但一致性和查询能力取决于具体产品。

选型应从访问模式、事务边界、数据关系、容量增长、运维能力和恢复目标出发，而不是因为某个数据库“更潮”。很多系统会用关系库保存事实数据，用缓存或搜索引擎承接读性能，用向量库承接相似度检索。

### 2. 数据库 schema 应该如何设计？

**面试问法**：设计表结构时先考虑哪些问题？

**参考答案**：先确定实体、生命周期、唯一性和关系，再定义字段类型、可空性、默认值、主键和约束。字段应表达稳定业务事实，避免把多个含义塞进一个字符串，也不要过早把所有数据都做成无结构 JSON。

还要考虑查询路径、数据量、冷热分层、审计和迁移。Agent 会话至少要明确会话、消息、工具调用、模型调用和版本之间的关系，避免把整个状态序列化进一列后无法按租户、时间和状态检索。

### 3. 主键和外键有什么作用？

**面试问法**：为什么不能只用业务字段当主键？

**参考答案**：主键唯一标识一行记录，外键表达表之间的引用关系并可防止孤儿数据。业务字段可能变化、过长或包含隐私，通常会使用稳定的数值或 UUID 主键，再为真正的业务唯一字段建立唯一约束。

外键约束能提高数据完整性，但高并发、分库分表或跨服务场景可能选择应用层约束和异步校验。无论是否使用数据库外键，都要明确删除、归档和重试时的引用行为。

### 4. 什么是数据库范式？为什么会反范式？

**面试问法**：第三范式解决什么问题？

**参考答案**：范式通过拆分重复和依赖不合理的数据，减少更新异常、插入异常和删除异常。常见设计会让每个字段依赖于主键，并把独立实体拆到不同表中，通过外键关联。

反范式是有意识地复制或汇总数据，以减少复杂关联和读取成本。它会增加写入和一致性维护负担，因此要有明确的更新策略、校验任务和可接受的延迟，不能只是为了少写一次 JOIN 就复制所有字段。

### 5. 索引解决什么问题？

**面试问法**：为什么索引能加快查询，也会拖慢写入？

**参考答案**：索引是为特定访问模式建立的额外有序或哈希结构，可以减少扫描的数据量。数据库在插入、更新和删除时需要同步维护索引，因此索引越多，写放大、存储和缓存压力越大。

索引应围绕真实的过滤、排序、连接和范围查询建立。低选择性字段、很少使用的字段或频繁更新的大字段不一定适合单独建索引，最终要通过执行计划和线上指标验证。

### 6. B+ 树索引为什么常见？

**面试问法**：B+ 树相对二叉树有什么优势？

**参考答案**：B+ 树每个节点可以容纳很多 key，树高较低，适合按磁盘页读取；叶子节点按顺序连接，既能快速定位，也能高效执行范围扫描。索引层级少意味着随机 I/O 次数更少。

索引并不是把所有列都放进去。索引宽度会影响缓存命中、写入和回表成本，设计时要结合最常见的查询条件、排序顺序和数据分布。

### 7. 联合索引的最左匹配原则是什么？

**面试问法**：索引 `(tenant_id, status, created_at)` 能支持哪些查询？

**参考答案**：联合索引按列顺序组织，通常能有效支持从最左列开始的连续条件，例如按租户查询、按租户和状态查询，或在前缀等值后按时间范围查询。跳过最左列后，后面的列通常不能充分利用索引的有序性。

实际优化还要考虑优化器、选择性、排序、覆盖索引和数据分布。不能只看 WHERE 子句是否包含字段，还要查看 `EXPLAIN` 里实际使用的索引、扫描行数和回表情况。

### 8. 什么是覆盖索引？

**面试问法**：为什么加一个看似多余的列可以减少查询耗时？

**参考答案**：如果索引已经包含查询过滤和返回所需的全部字段，数据库可以直接从索引页返回结果，不必再根据主键回到数据页，这叫覆盖索引。它能减少随机 I/O，尤其适合高频列表查询。

覆盖索引会增加索引宽度和写入成本，不应把大文本、完整 JSON 或低频字段全部塞进去。对分页列表，可以只覆盖必要的摘要字段，再按需读取详情。

### 9. 如何看执行计划？

**面试问法**：`EXPLAIN` 里重点看哪些信息？

**参考答案**：重点看是否使用预期索引、访问类型、估算和实际扫描行数、过滤比例、排序或临时表、连接顺序以及回表次数。估算行数和真实行数差异很大时，可能是统计信息过期、数据分布偏斜或条件相关性导致优化器判断失误。

优化不能只看计划变得“更复杂”。应在代表性数据量和真实参数下比较总耗时、P95、CPU、I/O 与锁等待，并确认修改没有让其他查询退化。

## 二、事务与并发控制

### 10. ACID 分别是什么？

**面试问法**：事务的四个特性如何落到实际？

**参考答案**：原子性要求事务中的操作要么全部成功、要么全部回滚；一致性要求事务前后满足约束；隔离性控制并发事务之间的可见性；持久性要求提交后的结果在故障恢复后仍能保留。

ACID 不是单一开关，隔离级别、日志、锁、存储引擎和故障恢复共同实现它。跨服务业务通常无法靠一个本地事务覆盖，需要幂等、消息、补偿或 Saga 等方案。

### 11. 事务隔离级别有哪些？

**面试问法**：读未提交、读已提交、可重复读和串行化分别解决什么？

**参考答案**：读未提交允许看到其他事务尚未提交的变化，隔离最弱；读已提交避免脏读，但同一事务两次读取可能得到不同结果；可重复读保证同一事务重复读取已读行的一致性；串行化通过更强的锁或冲突控制模拟串行执行，安全但并发度最低。

不同数据库的实现细节不同，有的通过 MVCC，有的结合锁和快照。选择隔离级别要根据业务是否允许重复读、范围幻读和写冲突，而不是盲目使用最高级别。

### 12. 脏读、不可重复读和幻读是什么？

**面试问法**：三种并发异常分别举例说明。

**参考答案**：脏读是读到另一个事务尚未提交、之后可能回滚的数据；不可重复读是同一事务两次读取同一行，期间被其他事务提交修改；幻读是同一范围查询两次，第二次多出或少了符合条件的行。

MVCC 可以通过快照减少读写阻塞，但范围写入和唯一性约束仍可能需要锁。面试时要说明异常是否真正影响业务，例如统计报表和扣库存的正确性要求不同。

### 13. MVCC 是怎么工作的？

**面试问法**：为什么读操作可以不阻塞写操作？

**参考答案**：多版本并发控制为记录保留多个版本，事务根据自己的快照和可见性规则读取合适版本，写入则产生新版本。这样普通读不必等待写锁，读写并发度较高。

旧版本需要被清理，长事务会阻止回收并扩大存储和扫描成本。使用 MVCC 并不意味着完全没有锁，更新冲突、唯一索引、范围写入和 DDL 仍可能等待。

### 14. 悲观锁和乐观锁怎么选？

**面试问法**：库存扣减应该用哪种锁？

**参考答案**：悲观锁假设冲突常见，先锁住记录再修改，适合冲突高且临界区短的场景；乐观锁不预先阻塞，通过版本号、时间戳或条件更新检测冲突，适合读多写少或冲突较低的场景。

库存扣减可以使用 `UPDATE ... SET stock = stock - 1 WHERE stock > 0` 这类原子条件更新，避免先读后写的竞态。无论哪种方式，都要处理失败重试、超时、死锁和幂等，不能只在代码里加一个布尔判断。

### 15. 数据库死锁如何定位？

**面试问法**：两个事务互相等待时怎么办？

**参考答案**：数据库通常会检测等待环并回滚其中一个事务。定位需要查看死锁日志、事务 SQL、锁顺序、索引范围和持锁时间，找出为何两个路径以不同顺序访问资源。

预防方式包括统一访问顺序、缩短事务、为条件建立合适索引、避免在事务中调用外部服务，并在应用层对可重试的死锁错误做有限退避重试。重试必须是幂等的，不能把死锁简单吞掉。

### 16. WAL 和数据库恢复有什么关系？

**面试问法**：数据库断电后如何恢复已提交事务？

**参考答案**：预写日志要求数据页落盘前先把描述变更的日志写入稳定存储。崩溃恢复时，数据库可以重做已经提交但数据页尚未写回的操作，并回滚未完成事务，从而恢复一致状态。

WAL 让随机数据页写入可以延后和批量化，但日志本身会带来写放大和磁盘压力。提交延迟、日志盘吞吐、checkpoint 和归档策略都会影响恢复时间和数据丢失窗口。

### 17. 主从复制解决什么问题？

**面试问法**：读写分离有什么好处和坑？

**参考答案**：主从复制把写入集中到主库，再把变更传播到一个或多个副本，可以扩展读吞吐、提供故障切换和备份来源。副本通常存在延迟，因此刚写入的数据不一定能立即从从库读到。

需要“写后读一致”时，可以在一段时间内读主库、携带位点等待副本追上，或由业务接受最终一致。复制不能替代备份，删除和错误写入也会被复制到副本。

## 三、性能、缓存与扩展

### 18. 如何排查慢查询？

**面试问法**：一个查询从 20ms 变成 2s，你怎么开始？

**参考答案**：先确认耗时是在数据库执行、连接池排队、锁等待还是应用处理；再收集真实 SQL、参数、执行计划、扫描行数、排序、临时表和锁信息。比较正常和异常时间段的数据量、统计信息、索引变化及资源使用。

修复可能是增加或调整索引、改写查询、减少返回列、拆分大事务、更新统计信息或归档冷数据。优化后要在代表性数据和并发下验证 P95/P99，不能只用一条小样例查询证明成功。

### 19. Offset 分页和游标分页有什么区别？

**面试问法**：为什么数据量大时 `LIMIT 100000, 20` 会变慢？

**参考答案**：Offset 分页需要定位并跳过前面的记录，偏移越大，扫描和丢弃成本通常越高；并发插入或删除还可能导致页之间重复或漏项。游标分页根据稳定排序键记录上一页最后位置，例如 `(created_at, id)`，下一页从该位置继续查。

游标分页性能更稳定，但不能随意跳到任意页，需要设计 opaque cursor 并校验过滤条件没有变化。排序键必须唯一或带唯一 tie-breaker，否则会出现边界重复。

### 20. 连接池如何设置？

**面试问法**：连接池越大越好吗？

**参考答案**：连接池限制应用同时占用数据库连接的数量，减少频繁握手和认证。池太小会让请求排队，池太大则可能耗尽数据库线程、内存和锁资源，导致所有请求变慢。

池大小应由数据库最大连接数、实例数量、请求并发、事务时长和下游容量共同决定。必须设置获取连接超时、空闲回收、健康检查和应用关闭时的释放，并监控活跃、空闲和等待连接数。

### 21. 缓存一致性有哪些常见方案？

**面试问法**：数据库更新后，缓存如何同步？

**参考答案**：Cache Aside 通常是读时缓存未命中再查库，写时先更新数据库再删除缓存；Write Through 让写入同时更新缓存和存储；Write Behind 先写缓存再异步落库，延迟低但丢数据风险更高。

常见实践是以数据库为事实来源，更新成功后删除缓存，读取时重建，并通过版本号、消息失效、短 TTL 和双删降低不一致窗口。必须明确允许多长时间的旧数据，以及删除失败和并发重建如何处理。

### 22. 什么是缓存穿透、击穿和雪崩？

**面试问法**：缓存失效后数据库被打爆，怎么防？

**参考答案**：穿透是大量请求查询本来不存在的数据，无法命中缓存；击穿是一个热点 key 过期时大量请求同时回源；雪崩是大量 key 同时过期或缓存整体不可用。三者都可能把压力集中到数据库或下游服务。

可以使用空值缓存或 Bloom Filter 防穿透，热点 key 加互斥重建、逻辑过期或预热防击穿，TTL 加随机抖动、分批失效和限流降级防雪崩。缓存保护必须与数据库连接池和熔断一起设计。

### 23. Redis 常用数据结构如何选？

**面试问法**：字符串、Hash、List、Set、ZSet 分别适合什么？

**参考答案**：字符串适合计数、标志和简单缓存；Hash 适合一组字段；List 可做简单队列；Set 适合去重和集合运算；ZSet 适合带分数的排行榜、延迟队列或按时间排序。实际还要考虑单 key 大小、持久化、淘汰和热点分布。

Redis 不是所有数据库问题的替代品。需要复杂事务、范围关联和可靠历史记录时，应把事实数据保存在关系库或专门存储，Redis 作为缓存、索引或短期协调层。

### 24. 分库分表和分区有什么区别？

**面试问法**：表数据太大时先做分区还是分表？

**参考答案**：分区通常仍在一个数据库实例内，由数据库按范围、列表或哈希把一张逻辑表拆成多个物理分区；分库分表把数据拆到不同库或实例，能够突破单实例容量和连接瓶颈，但查询、事务和运维更复杂。

如果主要问题是时间范围扫描和归档，分区可能足够；如果单实例 CPU、存储或连接已经到上限，才考虑分片。分片键要兼顾数据均衡、查询路由、租户隔离和跨分片聚合。

### 25. 什么是幂等写入和 Upsert？

**面试问法**：网络重试时如何避免重复创建订单？

**参考答案**：幂等写入为每次业务操作提供唯一键，重复请求会返回第一次处理结果或相同最终状态。数据库可以通过唯一约束、`INSERT ... ON CONFLICT`、版本号和状态机保证同一个业务键不会被并发重复处理。

幂等记录要和业务结果保持一致，不能先写“已处理”再因为事务失败而没有订单。对外部支付、模型任务或工具调用，还需要保存请求状态、响应摘要和可重试错误。

### 26. 软删除有什么利弊？

**面试问法**：为什么不直接物理删除？

**参考答案**：软删除通过状态或删除时间保留记录，便于审计、恢复和引用追踪；代价是所有查询都要正确过滤，唯一约束、索引膨胀和隐私删除要求会更复杂。

可以为活跃数据建立部分索引，定期把过期软删除数据归档或物理清理。涉及个人数据时，软删除不等于满足真正的删除义务，应单独设计脱敏、密钥销毁和备份生命周期。

### 27. 数据库迁移如何做到可回滚？

**面试问法**：生产环境变更表结构为什么不能只跑一条 ALTER？

**参考答案**：迁移应尽量向后兼容，先扩展结构再升级应用，最后收缩旧字段。大表变更要评估锁、重建时间、复制延迟和磁盘空间，必要时使用在线 DDL、分批回填和限速任务。

回滚不一定是执行反向 SQL，数据已经写入新结构后可能无法无损回退。更可靠的做法是保留旧路径、备份和校验，准备前向修复、停止写入或切换旧版本的方案。

## 四、Agent 数据存储

### 28. 会话消息表应该如何设计？

**面试问法**：多轮对话怎么存，才能支持重放和审计？

**参考答案**：至少区分租户、用户、会话、消息、消息顺序、角色、内容版本、父消息、创建时间和状态。模型调用、工具调用、token 消耗和错误应作为可关联的事件或明细表，而不是覆盖在消息文本里。

消息最好追加写入，编辑和摘要通过新版本或派生记录表示，便于重放和审计。查询索引通常围绕 `tenant_id + conversation_id + sequence`，并对大内容做冷热分层和访问权限控制。

### 29. 向量数据库和关系数据库如何分工？

**面试问法**：有了向量库，为什么还需要关系库？

**参考答案**：关系库擅长事务、唯一性、权限、结构化过滤和审计；向量库擅长向量近邻搜索、分片和索引构建。RAG 系统通常把文档、版本、租户权限和处理状态放在关系库，把向量和分块索引放在向量存储，并保存可回溯的文档 ID 和版本号。

不能只保存向量而丢掉原文和权限信息。检索结果在返回给模型前要再次做租户、文档版本和访问控制过滤，删除文档时还要同步清理向量索引和缓存。

### 30. Agent 记忆库如何区分短期和长期记忆？

**面试问法**：对话历史和用户偏好是否应该放在同一张表？

**参考答案**：短期记忆服务于当前运行上下文，通常保留最近消息、工具结果和任务状态；长期记忆保存经过确认的用户偏好、事实和历史摘要，需要来源、置信度、更新时间和删除机制。两者的生命周期、写入门槛和隐私风险不同。

长期记忆不能把模型猜测直接当成事实。应记录来源和版本，允许用户查看、修改和删除，并在检索时按任务、租户和权限过滤。对话窗口则可以通过摘要、滑动窗口和重要性评分控制 token。

### 31. 数据库如何支持多租户隔离？

**面试问法**：同一套服务如何防止租户串数据？

**参考答案**：每张业务表都应有明确的租户归属，查询和写入在数据访问层统一注入租户条件，并用数据库策略、行级安全或独立 schema/实例增加防线。缓存 key、对象存储路径、向量集合和日志也必须带租户维度。

隔离方案可以从共享表逐步演进到分 schema 或分库，但都要测试越权查询、后台任务、导出、重试和缓存命中。不要只依赖前端传来的 tenant_id，服务端应从认证上下文确定它。

### 32. 如何设计数据库备份和恢复？

**面试问法**：有备份就等于能恢复吗？

**参考答案**：备份要结合恢复点目标和恢复时间目标，决定全量、增量、日志归档和保留周期。恢复演练要验证备份可读、权限和密钥可用、应用能否连接，以及从故障时刻恢复到可服务状态需要多久。

备份应跨故障域保存并加密，恢复测试不能只检查文件存在。Agent 的会话、评测数据和文档索引还要明确哪些可以重建，哪些是不可替代的业务事实。

### 33. 如何处理数据库连接和事务中的外部调用？

**面试问法**：事务里能不能直接调用模型 API？

**参考答案**：通常不应在持有数据库事务和锁的同时调用慢速外部服务，因为网络等待会延长锁持有时间、增加死锁和连接池耗尽风险。更常见的做法是先提交业务状态，再通过消息或任务表异步调用外部服务，结果回写时使用幂等状态机。

如果必须同步返回，要缩短事务边界并设置严格截止时间，确保失败可以回滚或补偿。数据库事务保证本地事实，外部调用通过重试、幂等键和补偿保证最终状态。

### 34. 数据库查询如何防止提示词注入和越权？

**面试问法**：RAG 或 Agent 生成 SQL 时怎么保证安全？

**参考答案**：模型生成的 SQL 或过滤条件必须经过解析、参数化和权限校验，不能直接拼接执行。数据库账号采用最小权限，读写分离，危险操作需要人工审批或白名单；查询还要设置超时、返回行数和资源限制。

对于自然语言转 SQL，应把允许访问的 schema、字段和租户范围作为服务端约束，而不是只写在提示词里。日志记录查询摘要和拒绝原因，避免记录完整敏感数据。

### 35. 如何为 Agent 选择数据库组合？

**面试问法**：一个生产级 Agent 通常需要哪些存储？

**参考答案**：可以用关系库保存账号、租户、会话元数据、任务状态、审计和评测结果；用对象存储保存原始文档、大文件和归档；用向量索引做语义召回；用 Redis 做短期缓存、限流和任务协调；必要时使用消息队列解耦异步处理。

组合不是越多越好。每增加一种存储，就增加一致性、备份、监控和运维成本。应先根据访问模式和可靠性要求确定事实来源，再通过可重建索引和缓存提升查询能力，确保删除、迁移、恢复和权限策略能够闭环。
