# 15.2 计算机网络

> 本节整理 50 道面向后端、Agent、平台工程岗位的高频网络面试题。每道题都尽量从“概念是什么、为什么这样设计、遇到问题怎么排查”三个层次回答。面试时不要只背协议名，最好能把它和一次真实的 API 请求、流式响应或超时故障联系起来。

## 一、网络分层与请求基础

### 1. OSI 七层模型和 TCP/IP 模型有什么区别？

**面试问法**：OSI 和 TCP/IP 分别怎么分层？实际开发为什么更多使用 TCP/IP 模型？

**参考答案**：OSI 是便于教学和分析的七层模型，从下到上是物理层、数据链路层、网络层、传输层、会话层、表示层和应用层。TCP/IP 通常概括为网络接口层、网际层、传输层和应用层。实际协议栈并不严格照着 OSI 实现，例如 TLS 常被放在传输层和应用层之间，HTTP、DNS、WebSocket 都属于应用层。

面试中可以这样落地：网卡和以太网负责链路，IP 负责跨网络寻址，TCP 或 UDP 负责端到端传输，HTTP 或自定义协议负责业务语义。分层的价值是隔离变化，一个应用可以在不改业务协议的情况下切换 TCP、QUIC 或不同的链路网络。

### 2. 一次 HTTP 请求经过了哪些封装和解封装？

**面试问法**：浏览器发出一个请求时，数据在各层分别增加了什么？

**参考答案**：应用层先生成 HTTP 请求行、请求头和请求体；传输层把应用数据放进 TCP 段或 UDP 数据报，加入端口、序号等信息；网络层再加上源 IP 和目标 IP；链路层最后加上 MAC 地址和帧校验。发送端是逐层封装，接收端则逐层解封装，最终把 HTTP 消息交给应用程序。

这种过程也解释了抓包时为什么能看到不同层的信息。HTTP 代理关注方法和状态码，TCP 诊断关注握手、重传和窗口，网络设备关注 IP 和路由，而网卡关注链路帧。某一层的故障不能简单归因到应用代码。

### 3. 从输入 URL 到收到响应，中间发生了什么？

**面试问法**：浏览器访问 `https://example.com/a` 的完整链路怎么讲？

**参考答案**：客户端先解析 URL，确定协议、主机、端口和路径，然后检查本地缓存、连接池和 DNS 缓存。若没有可复用连接，就通过 DNS 得到地址，建立 TCP 连接；HTTPS 还要进行 TLS 握手并校验证书。随后客户端发送 HTTP 请求，请求可能经过代理、负载均衡和 CDN，服务端处理业务并返回状态码、响应头和响应体。

响应到达后，客户端会根据缓存头决定是否保存，根据内容类型交给浏览器或 SDK 解析。排查慢请求时，应把总耗时拆成 DNS、连接建立、TLS、首字节、传输和客户端处理几个阶段，而不是只看服务端业务耗时。

### 4. DNS 查询过程是怎样的？

**面试问法**：输入域名后，DNS 是如何找到 IP 的？递归和迭代有什么区别？

**参考答案**：客户端通常先查浏览器、操作系统和本地递归解析器的缓存。递归解析器没有命中时，会从根域名服务器开始，查询顶级域名服务器，再查询负责目标域名的权威服务器，最后把结果缓存并返回客户端。客户端把请求交给递归解析器，递归解析器代表客户端完成多级查询，这叫递归；解析器逐级向其他服务器询问并自己继续下一步，属于迭代过程。

DNS 记录有不同用途。A 记录映射 IPv4，AAAA 记录映射 IPv6，CNAME 表示别名，NS 指定权威服务器，TXT 常用于验证。TTL 决定缓存时间，改 DNS 后并不会让所有客户端立刻看到新地址，所以发布切换需要预留传播时间。

### 5. TCP 和 UDP 的核心区别是什么？

**面试问法**：什么时候用 TCP，什么时候用 UDP？

**参考答案**：TCP 是面向连接的可靠字节流协议，提供有序传输、丢包重传、流量控制和拥塞控制，但建立连接和维护状态会带来开销。UDP 是无连接的数据报协议，不保证到达、顺序或不重复，协议头更简单，应用可以自行决定是否需要重传、排序和限速。

需要可靠请求响应、文件传输和大多数传统 HTTP 场景时通常使用 TCP。实时音视频、在线游戏、服务发现或希望由应用自定义可靠性时可能选择 UDP。HTTP/3 运行在 QUIC 之上，QUIC 使用 UDP 作为承载，但在用户态实现了可靠传输和多路复用，因此不能把“UDP”简单等同于“不可靠的业务协议”。

### 6. TCP 三次握手为什么需要三次？

**面试问法**：三次握手每一步做什么？两次或四次行不行？

**参考答案**：第一次由客户端发送 SYN，表示希望建立连接并携带初始序列号；第二次服务端返回 SYN+ACK，确认收到了客户端的序列号，同时告诉客户端自己的初始序列号；第三次客户端发送 ACK，确认收到了服务端的序列号。完成后双方都确认了对方的收发能力和初始序列号。

两次握手无法让服务端确认客户端确实收到了自己的 SYN+ACK，旧的延迟报文可能因此创建无效连接。三次已经足够完成双向确认，更多往返只会增加延迟。高并发服务端还要关注半连接队列和 SYN flood 防护，例如 SYN cookies、限速和连接层防火墙。

### 7. SYN flood 是什么？如何缓解？

**面试问法**：大量 SYN 请求为什么会拖垮服务器？

**参考答案**：服务端收到 SYN 后会分配半连接状态并回复 SYN+ACK，等待客户端最后的 ACK。如果攻击者持续发送伪造源地址的 SYN，服务器会积累大量未完成握手，占满半连接队列，正常客户端就可能无法建立连接。

常见缓解手段包括启用 SYN cookies、调大并合理监控半连接队列、限制单源或单网段速率，并在边缘负载均衡或防火墙层做清洗。应用层单纯增加线程数解决不了握手队列被耗尽的问题，防护要尽量靠近网络入口。

### 8. TCP 四次挥手为什么通常是四次？

**面试问法**：TCP 连接关闭和建立有什么不同？`FIN`、`ACK` 分别表示什么？

**参考答案**：TCP 是全双工连接，一方发送 FIN 只表示自己不再发送数据，但仍可以接收对方数据。主动关闭方先发送 FIN，被动方回复 ACK；被动方处理完剩余数据后再发送自己的 FIN；主动方最后回复 ACK。因此两个方向通常要分别关闭，形成四次挥手。

如果被动方恰好没有数据要发送，第二次 ACK 和自己的 FIN 也可能在实现上接近发送，但语义上仍然是两个方向的关闭。关闭时要确保应用已经读完缓冲区并正确处理半关闭，否则可能出现数据截断或连接泄漏。

### 9. TIME_WAIT 为什么存在？

**面试问法**：主动关闭连接的一方为什么会进入 TIME_WAIT？它太多怎么办？

**参考答案**：TIME_WAIT 通常持续两个最大报文段生命周期，主要有两个目的。第一，确保最后的 ACK 丢失后可以重发，让对方正常结束；第二，让旧连接中延迟到达的报文过期，避免它们被误认为新连接的数据。

短连接很多、客户端端口资源有限时，TIME_WAIT 会明显增加。应优先使用连接复用、连接池和合理的 keep-alive，检查是否有异常重试或服务端主动关闭。不要把简单开启端口复用当作唯一方案，因为错误配置可能导致旧报文和新连接混淆，且不同操作系统的语义并不相同。

### 10. TCP 如何保证可靠传输？

**面试问法**：TCP 的可靠性由哪些机制共同实现？

**参考答案**：TCP 为字节流分配序列号，接收端通过 ACK 确认已经收到的数据；发送端发现超时、重复 ACK 或选择性确认提示丢包时，会重传缺失数据。接收端按序重组，重复数据会被丢弃；发送和接收窗口则限制未确认数据量，防止一方无限发送。

可靠不代表永远不会失败。TCP 只能在连接仍然可用时尽力恢复，网络断开、对端进程崩溃或应用超时仍会让请求失败。业务层还需要设置超时、重试和幂等策略，不能把所有可靠性都交给 TCP。

### 11. 滑动窗口解决了什么问题？

**面试问法**：为什么 TCP 不等一个包确认后再发下一个？

**参考答案**：停等协议会让带宽和往返时延被严重浪费。滑动窗口允许发送端在没有收到确认前连续发送一段数据，窗口随着确认到达向前滑动。这样可以让链路上同时存在多个未确认报文，提高吞吐量。

TCP 窗口受到接收窗口和拥塞窗口共同约束，实际可发送量通常取两者较小值。窗口太大可能压垮接收端或网络，太小则吞吐不足。窗口缩放、选择性确认和高带宽时延网络优化，都是围绕这个机制展开的。

### 12. 流量控制和拥塞控制有什么区别？

**面试问法**：接收窗口和拥塞窗口分别管什么？

**参考答案**：流量控制解决“发送端太快，接收端来不及处理”的问题，接收端通过通告窗口告诉发送端自己还有多少缓冲空间。拥塞控制解决“网络中间设备和链路承载不了这么多数据”的问题，发送端根据丢包、延迟等信号调整拥塞窗口。

一个请求可能接收端很快但网络拥塞，也可能网络空闲但消费者处理很慢。前者由拥塞控制主导，后者由流量控制主导。排查吞吐下降时要同时看接收窗口、拥塞窗口、重传率和 RTT，不能只看服务器 CPU。

### 13. TCP 慢启动和拥塞避免是怎么工作的？

**面试问法**：TCP 为什么刚建立连接时速度较慢？

**参考答案**：TCP 不知道路径可以承受多大流量，因此通常从较小拥塞窗口开始，通过确认逐步增加发送量，这个阶段称为慢启动。达到阈值后进入拥塞避免，窗口增长更谨慎；检测到丢包时会降低窗口，重新寻找稳定点。

“慢启动”并不意味着传输一定很慢，而是避免新连接一开始就把网络打爆。短连接、跨地域高 RTT 或频繁重连会让连接不断重复慢启动，这也是连接复用和 HTTP/2、HTTP/3 多路复用能改善延迟的重要原因。

### 14. TCP 重传超时是如何估算的？

**面试问法**：RTO 为什么不能固定成一个常数？

**参考答案**：网络 RTT 会随路径、排队和负载变化，固定超时会在快网络上等待过久，也会在慢网络上误判丢包。TCP 会根据采样 RTT 估算平滑 RTT 和波动范围，再计算重传超时，并在连续超时时进行退避。

应用层也需要设置自己的请求超时，但它应该覆盖 DNS、连接、TLS、排队和响应读取等阶段。应用超时过短会在 TCP 尚未完成恢复时提前放弃，超时过长又会占用连接和协程，因此要基于真实分位数和重试预算设定。

### 15. Nagle 算法和延迟 ACK 会造成什么问题？

**面试问法**：小包交互为什么会出现额外延迟？怎么处理？

**参考答案**：Nagle 算法会把许多小写入合并，尽量减少网络上的小包数量；延迟 ACK 则可能等待一小段时间再确认，以便和数据一起发送。两者叠加时，交互式小消息可能出现不必要的等待。

低延迟 RPC、终端交互或实时控制场景会根据协议和测量结果考虑关闭 Nagle，或使用批量写入、明确的消息边界和合适的 ACK 策略。不能看到延迟就盲目设置 `TCP_NODELAY`，因为它可能增加包数量和 CPU、带宽开销。

## 二、HTTP、HTTPS 与实时通信

### 16. HTTP 为什么被称为无状态协议？

**面试问法**：HTTP 无状态是否意味着服务器不能保存用户状态？

**参考答案**：HTTP 语义上要求每个请求可以独立理解，协议本身不要求服务器记住上一次请求的上下文。无状态有利于缓存、负载均衡和横向扩展，但业务仍然可以通过 Cookie、Session ID、Token 或外部状态存储实现登录和会话。

因此“无状态”不是“没有状态”，而是状态不由 HTTP 连接自动承担。生产系统通常把会话放进共享缓存或数据库，并让应用节点保持尽可能少的本地会话依赖，这样请求才能自由分配到不同实例。

### 17. GET、POST、PUT、PATCH、DELETE 有什么区别？

**面试问法**：这些方法的语义和幂等性怎么解释？

**参考答案**：GET 用于获取资源，通常是安全且幂等的；POST 常用于创建子资源或触发动作，默认不保证幂等；PUT 表示用给定表示替换目标资源，设计上应当幂等；PATCH 用于部分修改，是否幂等取决于具体操作；DELETE 用于删除资源，重复删除通常应得到相同最终状态，因此常被设计为幂等。

幂等描述的是多次执行的最终效果，不代表每次响应完全一样，也不代表操作没有副作用。支付、下单等 POST 请求如果需要重试，通常要配合业务幂等键，而不是简单把 POST 改成 GET。

### 18. 常见 HTTP 状态码怎么分类？

**面试问法**：`200`、`201`、`204`、`301`、`400`、`401`、`403`、`404`、`409`、`429`、`500`、`502`、`503`、`504` 分别怎么用？

**参考答案**：2xx 表示请求已被成功处理，`200` 是一般成功，`201` 表示创建资源，`204` 表示成功但没有响应体。3xx 表示重定向或缓存相关处理。4xx 通常说明请求方需要修正参数、认证或权限，`401` 更接近“缺少有效认证”，`403` 是服务器理解请求但拒绝授权。

5xx 表示服务端或其依赖处理失败。`502` 常表示网关从上游拿到无效响应，`503` 表示暂时不可用或过载，`504` 表示网关等待上游超时。选状态码时要让客户端能据此决定是修参数、刷新认证、退避重试还是直接失败。

### 19. HTTP/1.1 的 keep-alive、Content-Length 和 chunked 有什么关系？

**面试问法**：HTTP/1.1 如何在复用连接时判断响应结束？

**参考答案**：持久连接允许一个 TCP 连接承载多个请求响应，减少重复握手。为了区分响应边界，服务端可以通过 `Content-Length` 指定固定长度，也可以使用 `Transfer-Encoding: chunked` 分块发送，最后用零长度块表示结束；如果连接关闭，也能表示响应结束，但会失去连接复用。

流式接口常用分块传输或直接保持连接并持续写入。代理、客户端和服务端必须对消息边界有一致理解，否则会出现响应截断、请求串线或连接无法复用的问题。HTTP/2 使用帧和流管理边界，不再依赖 HTTP/1.1 的文本分块语法。

### 20. HTTP/2 相比 HTTP/1.1 做了哪些改进？

**面试问法**：HTTP/2 的多路复用和头部压缩解决了什么问题？

**参考答案**：HTTP/2 把请求和响应拆成二进制帧，并在一条连接上复用多个独立流，减少了 HTTP/1.1 中为并发请求建立多个连接的需要。HPACK 压缩重复头部，流优先级和服务端能力也提供了更丰富的调度空间。

HTTP/2 并没有消除所有队头阻塞，因为多个流仍共享一条 TCP 连接，TCP 丢包可能让所有流等待。HTTP/2 适合大量小请求和连接复用，但是否更快仍取决于 TLS、代理、服务器配置和资源加载方式。

### 21. HTTP/3 和 QUIC 解决了什么问题？

**面试问法**：HTTP/3 为什么基于 UDP？它是不是不可靠？

**参考答案**：QUIC 在 UDP 之上实现可靠传输、加密握手、连接迁移和多路复用。每个流拥有独立的传输进度，一个流丢包不会像 TCP 那样阻塞同一连接上的所有流，因此减少了传输层队头阻塞。HTTP/3 使用与 HTTP/1.1、HTTP/2 相同的核心语义，只改变了消息承载方式。

选择 UDP 是为了让 QUIC 能在用户态快速演进并避免受制于内核 TCP 实现。QUIC 并不是把可靠性交给应用完全处理，连接确认、重传、拥塞控制和 TLS 都是协议的一部分。

### 22. TLS 握手主要做什么？

**面试问法**：HTTPS 建立连接时，客户端和服务端如何协商密钥？

**参考答案**：TLS 握手会协商协议版本和密码套件，服务端发送证书证明自己的身份，双方通过密钥交换算法建立共享会话密钥。之后应用数据通常使用高效的对称加密传输，并通过认证标签发现篡改。

非对称密码主要用于身份认证和密钥协商，对称密码负责大量数据加密。TLS 1.3 减少了握手往返并淘汰了许多旧算法，但安全性仍取决于证书校验、随机数、私钥保护和正确的协议配置。

### 23. HTTPS 如何防止中间人攻击？

**面试问法**：为什么“加密”还不够，证书验证有什么作用？

**参考答案**：只加密不认证，攻击者仍可能在客户端和服务端之间各建立一条加密连接。HTTPS 通过证书链把域名身份绑定到服务端公钥，客户端验证证书是否由受信任的 CA 签发、域名是否匹配、是否过期或被吊销，再进行密钥协商。

如果客户端关闭证书校验、信任任意自签名证书或把密码学错误吞掉，就可能被中间人劫持。内部服务可以使用私有 CA，但必须把根证书安全分发并严格校验，而不是在代码里写“忽略证书错误”。

### 24. CORS 解决什么问题？

**面试问法**：跨域请求为什么会被浏览器拦截？服务端怎么正确配置 CORS？

**参考答案**：同源策略限制一个源的脚本读取另一个源的响应，CORS 通过响应头明确授权哪些源、方法和请求头可以访问。它是浏览器的安全机制，服务端之间直接调用并不会因为 CORS 被限制。

服务端应精确返回允许的 `Origin`，并按需设置 `Access-Control-Allow-Methods`、`Access-Control-Allow-Headers` 和凭据策略。允许凭据时不能把 `Access-Control-Allow-Origin` 设为任意星号，并要注意缓存代理按 `Origin` 区分响应，必要时加入 `Vary: Origin`。

### 25. CORS 预检请求什么时候发生？

**面试问法**：什么是 `OPTIONS` 预检？为什么浏览器先发一个请求？

**参考答案**：当跨域请求不是“简单请求”时，浏览器会先发送 `OPTIONS`，告诉服务端实际请求的方法、请求头和来源，服务端通过 CORS 响应头确认是否允许。带自定义认证头、非简单方法或某些内容类型时常会触发预检。

预检会增加一次往返，服务端可以通过 `Access-Control-Max-Age` 在合理期限内缓存授权结果。排查跨域问题要分别看预检是否成功、实际请求是否发出，以及响应头是否在错误响应上也正确返回。

### 26. Cookie、Session 和 Token 有什么区别？

**面试问法**：登录状态应该放在哪里？Cookie 和 Token 是一回事吗？

**参考答案**：Cookie 是浏览器自动按域和路径附带的客户端存储机制；Session 是服务端保存的会话状态，Cookie 中通常只保存 Session ID；Token 是一段由客户端主动携带的凭证，可以是有状态的随机值，也可以是自包含的 JWT。

Cookie 可以设置 `Secure`、`HttpOnly`、`SameSite` 等属性来降低窃取和跨站请求风险。把 Token 放在 Cookie 还是 Authorization 头，要结合浏览器行为、跨站需求、XSS 和 CSRF 防护设计，不能简单说某一种永远更安全。

### 27. JWT 的优缺点是什么？

**面试问法**：JWT 为什么适合分布式系统？如何处理注销和撤销？

**参考答案**：JWT 通常包含头部、载荷和签名，服务端可以在不查询会话数据库的情况下验证签名和过期时间，因此适合无状态认证和跨服务传递身份。它并不默认加密，敏感信息不能直接放在载荷里；签名算法、密钥轮换和受众校验都必须严格配置。

JWT 一旦签发，在过期前通常仍然有效，主动注销和权限变更不如中心化 Session 直接。常见做法是短时访问令牌配合刷新令牌、令牌版本号或撤销列表，并限制载荷大小和可用范围。

### 28. HTTP 缓存是如何工作的？

**面试问法**：浏览器、CDN 和服务端缓存如何判断能不能复用响应？

**参考答案**：缓存会根据请求方法、目标 URL、响应头和缓存策略保存响应。`Cache-Control: max-age` 说明在一定时间内可以直接复用，`no-store` 禁止保存，`no-cache` 通常表示使用前要向源站验证，而不是完全不缓存。

缓存键不能只看 URL，还要考虑 `Vary` 指定的请求头、认证信息和内容协商。公共缓存不能错误地复用带用户私密数据的响应，服务端应明确设置可缓存范围和失效策略。

### 29. ETag 和 Last-Modified 有什么区别？

**面试问法**：条件请求如何避免重复传输整个响应？

**参考答案**：`ETag` 是资源表示的版本标识，客户端下次请求带 `If-None-Match`，服务端确认未变化后返回 `304 Not Modified`。`Last-Modified` 使用时间戳，客户端通过 `If-Modified-Since` 进行验证。

ETag 通常比时间戳更精确，适合内容可能在同一秒内多次变化的场景；时间戳实现简单，适合作为补充。响应为 304 时不需要重复发送正文，但仍要返回足够的缓存元数据，客户端才能继续正确使用缓存。

### 30. CDN 为什么能加速静态资源？

**面试问法**：CDN 节点离用户更近，具体快在哪里？

**参考答案**：CDN 把可缓存的资源复制到多个边缘节点，用户请求先到较近的节点，命中缓存时无需回源站跨地域传输。这样可以降低 RTT、减轻源站带宽和连接压力，并能在边缘完成 TLS、压缩、限速和基础防护。

CDN 不是把所有动态接口都缓存。需要根据 URL、查询参数、Cookie、认证信息和 `Cache-Control` 控制缓存键，更新资源时使用版本化文件名或可靠的失效机制。缓存穿透、击穿和错误回源策略也要纳入设计。

### 31. 反向代理、网关和负载均衡有什么区别？

**面试问法**：Nginx、API Gateway、四层负载均衡分别承担什么角色？

**参考答案**：反向代理代表服务端接收客户端请求，可以做 TLS 终止、缓存、压缩和转发。负载均衡重点是把连接或请求分配到多个后端，既有按 IP、连接的四层方式，也有按 HTTP 路径、权重和健康状态的七层方式。API 网关通常在此基础上增加认证、路由、限流、协议转换和审计。

这些角色可以部署在同一组件中，但职责和故障边界要分清。出现 `502` 时应检查代理与上游的连接、协议和响应格式；出现后端热点时应检查负载算法、连接池和会话粘性，而不是只增加实例数。

### 32. WebSocket 和 HTTP 有什么区别？

**面试问法**：为什么 WebSocket 适合实时双向通信？

**参考答案**：WebSocket 通常先通过 HTTP Upgrade 建立连接，随后使用帧协议在同一连接上实现客户端和服务端的双向主动发送。HTTP 传统上是请求驱动的，服务端需要借助轮询、长轮询或 SSE 才能持续推送。

WebSocket 适合双向低延迟场景，如协作编辑、在线游戏和实时控制。设计时仍要考虑心跳、断线重连、消息顺序、背压、连接上限和权限续期。长连接不是越多越好，代理、负载均衡和服务端资源都要有相应容量。

### 33. SSE 和 WebSocket 怎么选？

**面试问法**：Agent 流式输出用 SSE 还是 WebSocket？

**参考答案**：SSE 基于普通 HTTP，服务端通过 `text/event-stream` 持续发送事件，浏览器的 `EventSource` 会自动处理重连和事件分发。它是单向通道，客户端仍通过普通 HTTP 请求发送指令，适合模型 token 流、任务进度和通知推送。

WebSocket 提供双向通信，协议和连接管理更复杂，适合客户端和服务端都需要频繁主动发送的场景。Agent 对话若只是“客户端发一次、服务端持续输出”，SSE 往往更简单；若需要双向工具控制、多人协作或实时输入，则考虑 WebSocket。

### 34. 长轮询和短轮询有什么差异？

**面试问法**：没有 WebSocket 时如何实现服务端推送？

**参考答案**：短轮询是客户端按固定间隔反复请求，无论有没有新数据都得到响应，简单但会产生大量空请求。长轮询会让服务端暂时挂起请求，直到有数据或超时再返回，客户端随后立即发起下一次请求，能够减少空转。

长轮询仍然受连接数、代理超时和重试风暴影响，并且每次消息都要重新建立请求上下文。选择方案要看消息频率、客户端环境和基础设施支持，能使用 SSE 或 WebSocket 时通常优先使用更贴合场景的长连接协议。

### 35. gRPC 和 REST 怎么选？

**面试问法**：gRPC 的优势是什么？为什么对外 API 仍常用 REST？

**参考答案**：gRPC 通常基于 HTTP/2 和 Protocol Buffers，接口由 schema 定义，支持强类型代码生成、流式调用和高效二进制编码，适合内部服务间调用。REST 以资源和 HTTP 语义为中心，调试、浏览器兼容和跨语言接入更直接，适合作为开放 API 或前端接口。

选择时要考虑客户端生态、可观测性、网关支持、版本兼容和调试成本。内部高吞吐调用不一定必须 gRPC，外部 API 也不一定必须 REST，关键是把契约、错误模型、超时和重试语义定义清楚。

### 36. HTTP 流式响应和一次性 JSON 响应有什么区别？

**面试问法**：Agent 为什么要流式返回 token？服务端要注意什么？

**参考答案**：一次性 JSON 需要服务端完成全部生成后再返回，客户端实现简单但首字节和首屏等待较长。流式响应会在结果产生时分段发送，降低首 token 延迟并让用户看到进度，但客户端要处理半包、断线、结束标记和中间错误。

服务端要关闭不必要的缓冲，正确设置 `Content-Type` 和缓存策略，并在代理层确认不会把全部内容攒完才转发。还要设置空闲超时和心跳，避免中间设备认为连接已经失效。

### 37. 什么是请求幂等？如何为接口设计幂等？

**面试问法**：网络超时后客户端能不能安全重试？

**参考答案**：幂等表示同一个请求执行一次或多次，资源最终状态相同。GET、PUT、DELETE 通常可以设计成幂等，但是否幂等由业务语义决定。支付、发货、创建任务等动作即便使用 POST，也可以通过客户端生成的幂等键让重复请求返回第一次处理结果。

服务端需要持久化幂等键、请求指纹和处理状态，并在并发请求到来时使用唯一约束或事务保证只有一个请求真正执行。幂等记录要设置合理保留时间，错误重试不能无限占用存储。

### 38. 重试为什么要指数退避和抖动？

**面试问法**：接口失败后为什么不能立即连续重试三次？

**参考答案**：立即重试会让已经过载的服务收到更多请求，形成重试风暴。指数退避让等待时间逐次增长，抖动则给等待时间加入随机性，避免大量客户端在同一时刻再次发送。

只对暂时性错误重试，例如连接失败、部分 5xx 或明确的限流响应；参数错误、权限错误通常不应重试。每次重试要继承总截止时间，设置最大次数，并配合幂等键、熔断和限流，避免把一次失败放大成级联故障。

### 39. 网络请求应设置哪些超时？

**面试问法**：为什么一个 `timeout=5` 不够说明问题？

**参考答案**：至少要区分连接超时、TLS 握手超时、从连接池获取连接的等待时间、读取首字节超时、分段读取超时和整个请求截止时间。连接成功但服务端长时间不返回首字节，和响应流正在持续传输，应该采用不同的判断。

超时需要从用户体验和下游预算反推。例如上游总预算只有 10 秒，重试两次就不能让每次请求都单独等待 10 秒。日志要记录各阶段耗时和最终超时类型，否则只能看到“请求超时”而无法定位瓶颈。

### 40. 连接池有什么作用？

**面试问法**：为什么 HTTP 客户端不应该每次请求都新建 Client？

**参考答案**：连接池可以复用 TCP、TLS 和 HTTP/2 连接，减少握手开销，并限制同时建立的连接数。它还可以复用 DNS、保持连接活跃并集中管理超时和代理配置。

每次请求新建客户端会导致连接无法复用、文件描述符和端口快速消耗，甚至触发服务端连接洪泛。连接池要设置最大连接数、空闲回收、保活和获取连接超时，并在应用退出时显式关闭。

## 三、故障定位与工程实践

### 41. DNS 解析失败应该怎样排查？

**面试问法**：服务偶发“域名解析失败”，你从哪里开始？

**参考答案**：先确认失败发生在客户端、容器、节点还是递归解析器，使用 `dig`、`nslookup` 或语言运行时日志查看查询类型、响应码和耗时。再检查本地 DNS 配置、搜索域、缓存、网络策略、权威服务器可用性和 TTL。

要区分 `NXDOMAIN`、超时、SERVFAIL 和返回空记录。容器环境常有独立的 DNS 转发链路，宿主机能解析不代表容器能解析。临时改 hosts 可以验证方向，但不能作为生产修复，因为它绕开了服务发现和故障切换。

### 42. `502`、`503`、`504` 如何定位？

**面试问法**：网关返回 5xx 时，网关和业务服务谁有问题？

**参考答案**：`502` 重点检查网关是否连到了错误端口、上游是否提前断开、响应是否违反协议或 TLS 配置不匹配；`503` 重点看上游是否没有健康实例、过载、主动拒绝或触发熔断；`504` 重点看上游处理时间、连接池排队、网络丢包和网关超时配置。

定位时要把网关请求 ID 与上游日志关联，比较网关计时和应用计时。如果网关等待了 30 秒而应用日志只有 2 秒，可能是连接或代理链路问题；如果应用本身耗时超过截止时间，则应从数据库、外部 API 或锁等待继续下钻。

### 43. MTU、分片和 PMTUD 是什么？

**面试问法**：为什么某些大响应在特定网络下失败，小响应却正常？

**参考答案**：MTU 是一条链路能承载的最大 IP 包大小。超过路径某一跳 MTU 的数据可能需要分片，IPv6 中中间路由器不负责分片，依赖端点根据路径信息调整。路径 MTU 发现通过探测和 ICMP 等反馈确定合适的包大小。

防火墙错误丢弃 ICMP、隧道封装或 VPN 可能造成 PMTUD 黑洞，表现为小包正常、大包卡住。排查时要检查链路 MTU、隧道开销、分片计数和 ICMP 可达性，并避免简单地把所有接口 MTU 调到很小而牺牲吞吐。

### 44. NAT 做了什么？为什么会影响长连接？

**面试问法**：私网机器如何访问公网？NAT 为什么会导致连接断开？

**参考答案**：NAT 把私网地址和端口映射到公网地址和端口，使多个内网主机共享公网地址。映射表通常会因空闲超时而删除，所以长时间没有数据的 TCP、WebSocket 或 SSE 连接可能在 NAT 设备处失效。

长连接应设计应用层心跳或保活，并让心跳间隔小于链路中最短的空闲超时。NAT 还会消耗端口和连接表，突发短连接可能耗尽映射资源，因此连接复用、合理的池大小和边缘容量都很重要。

### 45. IPv4 和 IPv6 有哪些主要差异？

**面试问法**：为什么迁移 IPv6 不只是把地址换成长一点？

**参考答案**：IPv4 地址空间有限，常依赖 NAT；IPv6 地址空间更大，地址配置、邻居发现和报文头设计也不同。IPv6 不使用广播，很多发现功能通过组播完成；应用还要正确处理地址族选择、DNS AAAA 记录和双栈连接。

双栈系统可能出现“IPv6 可解析但路径不可用”，因此客户端常采用 Happy Eyeballs 等策略并行尝试不同地址。日志和监控中要保留地址族信息，防止把 IPv6 故障误判成 DNS 或应用故障。

### 46. 端口和临时端口有什么作用？

**面试问法**：一个服务器能同时处理多少 TCP 连接？客户端端口为什么会耗尽？

**参考答案**：IP 标识主机，端口标识主机上的进程或服务。一个 TCP 连接由源 IP、源端口、目标 IP、目标端口和协议共同标识，因此同一客户端可以与同一服务端建立多个连接，只要源端口不同。

客户端发起连接时通常使用临时端口。大量短连接、TIME_WAIT 或连接池配置不当会耗尽临时端口，表现为无法建立新连接。排查时要看端口范围、连接状态、目标地址分布和应用是否错误地频繁创建客户端。

### 47. 如何用抓包定位一次请求失败？

**面试问法**：`tcpdump` 或 Wireshark 你重点看什么？

**参考答案**：先用请求 ID、五元组和时间范围缩小数据，再观察 DNS 是否返回、TCP 三次握手是否完成、TLS 是否成功、HTTP 请求是否发出以及响应码和 FIN/RST 的方向。重传、重复 ACK、窗口为零和异常 RTT 可以帮助判断网络质量或接收端压力。

HTTPS 正文通常不可直接查看，但仍能分析握手、证书、SNI、包长、时序和连接关闭。抓包要结合服务端访问日志、代理日志和客户端阶段耗时，单个抓包只能说明一条链路在某个时间点的行为。

### 48. Agent 调用模型 API 时，如何设计网络层？

**面试问法**：一个稳定的 Agent HTTP 客户端需要哪些能力？

**参考答案**：应统一封装连接池、DNS、TLS、分阶段超时、取消、重试、指数退避、幂等键、限流和结构化日志。流式响应要支持增量解析、心跳、断线续传或明确的不可续传策略；请求体和响应体要设置大小上限，避免异常数据拖垮内存。

还要把上游错误映射成业务可理解的结果，例如区分限流、认证失败、超时和模型拒答。日志中记录请求 ID、模型、首 token 延迟、总耗时、重试次数和响应大小，但不要记录 API Key、完整提示词或用户隐私。

### 49. 如何避免网络重试造成级联故障？

**面试问法**：下游变慢时，为什么上游也会一起挂？

**参考答案**：每一层都无条件重试会把一个下游请求放大成多倍流量，同时占满线程、协程和连接池，最终上游也超时。系统应在最靠近业务语义的一层决定是否重试，并把总截止时间、次数和预算向下游传递。

常见保护包括超时、舱壁隔离、并发上限、熔断、令牌桶限流、指数退避和随机抖动。恢复后要逐步放量，而不是瞬间让所有排队请求同时释放，避免“惊群”再次压垮服务。

### 50. 面试中如何回答“网络请求偶发变慢”的排查题？

**面试问法**：线上接口平均延迟正常，但 P99 偶发升高，你怎么定位？

**参考答案**：先按阶段拆解 P50、P95、P99，确认是 DNS、连接、TLS、排队、服务端处理、下游依赖还是响应传输变慢。再按地域、可用区、实例、协议版本、请求大小和错误类型切片，结合连接池、线程池、CPU、内存、GC、重传和下游指标寻找相关性。

如果是 Agent 流式接口，还要分别看首 token 延迟、token 间隔、总生成时间和客户端渲染时间。最终修复可能是连接复用、扩容热点实例、调整超时和池大小、修复慢查询或给下游增加限流；面试回答的关键是展示从现象到证据再到验证的闭环。
