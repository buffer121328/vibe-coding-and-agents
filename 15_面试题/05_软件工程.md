# 15.5 软件工程

> 本节用 25 道题覆盖软件工程的基础认知、协作方式、质量保障和 AI 协作。重点不是背流程名词，而是说明一个工程决策解决了什么问题、付出了什么代价，以及如何用证据验证结果。

## 一、工程认知与设计基础

### 1. 软件工程和“把代码写出来”有什么区别？

**面试问法**：为什么项目能运行还不代表工程做完了？

**参考答案**：写代码主要解决当前功能能否运行，软件工程还要解决需求是否正确、代码能否被多人维护、故障能否定位、版本能否升级、数据能否迁移以及系统能否长期交付。工程质量体现在可理解性、可测试性、可部署性、可观测性和可恢复性上。

面试时可以举一个具体例子：一个 Agent Demo 能调用模型并返回答案，但如果没有超时、权限、成本统计、失败重试和回归测试，就还没有达到可交付状态。

### 2. 什么是高内聚、低耦合？

**面试问法**：如何判断一个模块边界是否合理？

**参考答案**：高内聚表示一个模块中的代码围绕同一个明确职责组织，低耦合表示模块之间依赖少、接口稳定、变化相互隔离。模块边界不是按文件大小划分，而是看需求变化是否会集中在同一处，以及一个模块是否需要了解另一个模块的内部细节。

例如工具调用模块可以负责参数校验、超时和执行结果封装，但不应该直接修改会话 UI 或业务报表。这样更容易替换工具实现、独立测试，并在失败时复用统一的错误处理。

### 3. SOLID 原则在实际项目中怎么用？

**面试问法**：不要背定义，请说一个你真正使用过的原则。

**参考答案**：单一职责提醒我们不要让一个类同时负责路由、存储和通知；开闭原则鼓励通过扩展点增加模型供应商，而不是修改核心流程；依赖倒置要求核心业务依赖接口，具体数据库或 SDK 通过注入接入。接口隔离和里氏替换则帮助我们避免“实现了一个巨大接口但大部分方法无意义”。

这些原则不是越严格越好。小脚本如果为了抽象而抽象会增加复杂度，面试时要说明它是在什么变化压力下帮助了你，例如通过 `ModelClient` 协议替换同步 SDK 和测试假客户端。

### 4. KISS、DRY 和 YAGNI 如何平衡？

**面试问法**：重复代码一定要立刻抽象吗？

**参考答案**：KISS 鼓励保持实现简单，DRY 关注避免同一知识在多个地方重复，YAGNI 提醒不要为尚未验证的需求提前建设复杂能力。三者冲突时，应先识别重复的是业务规则还是偶然相似的代码，再根据变化频率决定是否抽象。

过早抽象会把两个还没有稳定的需求绑在一起，过晚抽象则会让规则分叉。通常先写清晰的重复实现，等第二或第三个真实用例出现后提取稳定边界，并用测试锁定行为。

### 5. 为什么要写设计文档？

**面试问法**：代码已经能看懂了，为什么还需要设计文档？

**参考答案**：设计文档记录问题边界、约束、方案、取舍和未决问题，帮助团队在写代码前暴露分歧。它还保存“为什么这样做”的历史，便于后来的人判断是否可以修改，而不是只从当前实现猜测意图。

好的设计文档不需要很长，但应包含目标、不做什么、关键流程、数据和接口、失败路径、容量假设、迁移计划和验证方式。Agent 场景中还要明确模型调用预算、权限边界、人工兜底和评估集。

### 6. 如何拆分一个需求？

**面试问法**：拿到“做一个智能客服”需求，你如何开始？

**参考答案**：先把目标拆成用户任务、成功标准和约束，再识别最小可交付路径。智能客服可能先拆为身份识别、知识检索、回答生成、转人工、审计和评估，而不是一开始就决定使用某个 Agent 框架。

每个切片都应有可验证的输入、输出和失败行为。先交付一条端到端闭环，再逐步增加复杂能力，可以尽早获得真实反馈，也能避免在没有数据和指标时堆叠架构。

### 7. 代码提交应该如何组织？

**面试问法**：为什么不建议把所有改动塞进一个巨型提交？

**参考答案**：一个提交最好表达一个可理解、可验证的变化，例如先加数据结构，再接入调用，再补测试和文档。这样 Review 更容易定位问题，回滚和二分排查也更安全。

提交信息应说明改变了什么和为什么，避免把格式化、无关重命名和功能修改混在一起。分支策略可以按团队规模选择，但无论使用主干开发还是短分支，都要让分支生命周期短、集成频繁。

### 8. Code Review 主要审什么？

**面试问法**：Review 是检查代码风格还是检查功能？

**参考答案**：Review 的第一目标是确认行为、边界和风险，其次才是风格。应重点看需求是否实现、错误路径是否安全、并发和资源是否受控、数据迁移是否可回滚、日志是否泄露敏感信息，以及测试是否证明了关键行为。

自动格式化、Lint 和类型检查应尽量交给工具，Review 时间留给架构、业务规则和难以自动发现的风险。评论要指向具体问题和建议，不把个人偏好伪装成必须修复的缺陷。

### 9. 测试金字塔是什么？

**面试问法**：单元测试、集成测试和端到端测试如何分工？

**参考答案**：测试金字塔强调用数量较多、反馈快速的单元测试覆盖局部逻辑，用数量适中的集成测试验证模块和真实依赖的连接，再用少量端到端测试验证关键用户路径。越靠近真实环境，成本和不稳定性通常越高。

这不是固定比例。数据库事务、鉴权和流式接口等关键边界可能需要更多集成测试；模型输出则应结合固定评测集和打桩，避免把不可重复的模型波动直接当成单测结果。

### 10. 单元测试和集成测试怎么区分？

**面试问法**：调用数据库的函数算单元测试吗？

**参考答案**：单元测试隔离外部依赖，验证一个函数或模块在给定输入下的行为；集成测试使用真实或接近真实的数据库、消息队列、HTTP 服务，验证边界协议、事务和配置是否正确。调用数据库的测试通常属于集成测试，除非数据库访问被替换成假实现。

两者都需要。单测适合快速覆盖分支和边界，集成测试能发现序列化、索引、事务和环境配置问题。测试命名和目录应明确类型，CI 可以分阶段运行。

### 11. Stub、Mock、Fake 有什么区别？

**面试问法**：为什么有时不应该只用 Mock？

**参考答案**：Stub 主要提供预设返回值，Mock 还可以验证调用次数、参数和顺序，Fake 则是一个能工作的简化实现，例如内存数据库。Mock 适合验证交互契约，但如果过度验证内部调用细节，重构实现却不改变行为时也会让测试大量失败。

测试应优先断言对外可观察结果和重要副作用。外部模型调用可以用 Fake 固定结构化响应，HTTP 客户端可以用 Mock 检查超时参数，而真正的协议兼容性仍应由少量集成测试覆盖。

### 12. 什么是 flaky test？如何治理？

**面试问法**：偶尔失败、重跑又通过的测试怎么办？

**参考答案**：Flaky test 的结果受到时间、并发顺序、网络、随机数、共享状态或环境差异影响，导致同一代码在相同输入下结果不稳定。它会降低团队对测试的信任，最终让真正的回归被忽略。

治理应先记录失败上下文，再区分测试本身的竞态、产品代码的竞态和外部依赖不稳定。使用固定时钟和随机种子、显式等待条件、隔离临时目录、清理共享数据，并修复根因；简单地重跑多次或标记跳过只能延后问题。

### 13. CI 应该检查什么？

**面试问法**：一条 Python 项目的 CI 流水线如何设计？

**参考答案**：至少应包括依赖安装、格式和静态检查、类型检查、单元测试、必要的集成测试、构建和安全扫描。关键路径可以在每次提交快速运行，完整测试在合并或定时任务中运行。

CI 环境必须尽量可复现，使用锁文件、明确的 Python 版本和最小权限凭证。失败日志要能定位具体步骤，外部服务测试应使用受控测试账号或 Fake，避免在 CI 中泄露密钥、消耗不可控费用。

### 14. 持续交付和持续部署有什么区别？

**面试问法**：代码通过 CI 后是不是应该自动上线？

**参考答案**：持续交付要求每次变更都处于可发布状态，但上线可能仍需要人工审批；持续部署则在满足自动化检查后自动发布到生产。两者都依赖小批量变更、可回滚版本、健康检查和发布后监控。

对支付、权限和模型成本等高风险变更，可以保留人工闸门或采用灰度、金丝雀和功能开关。自动化的目标不是取消判断，而是让重复检查可靠、让人把注意力放在真正的风险上。

### 15. 如何管理依赖和锁文件？

**面试问法**：为什么“写了版本范围”仍然不能保证可复现？

**参考答案**：直接依赖声明表达项目需要什么，传递依赖可能在不同时间解析出不同版本。锁文件记录完整依赖图和精确版本，CI 和生产应使用冻结安装，避免本地和部署环境出现差异。

依赖升级应分批进行，查看变更日志和安全公告，跑完整回归后再合并。不要为了临时绕过冲突直接手改环境；应更新声明、锁文件和兼容测试，让解决方案可被其他开发者复现。

### 16. 配置、密钥和代码如何分离？

**面试问法**：数据库密码和模型 API Key 应该放在哪里？

**参考答案**：代码仓库只保存配置结构和示例值，环境差异通过环境变量、配置文件或密钥管理服务注入。真实密钥不应提交 Git，也不应出现在日志、异常堆栈、截图和测试快照中。

配置加载时应做类型校验、默认值和启动期检查；高风险配置可以在运行时轮换。即使仓库是私有的，也应假设历史提交、CI 日志或构建产物可能被读取，发现泄露后要立即撤销和轮换。

### 17. 日志、指标和 Trace 如何配合？

**面试问法**：一个请求失败时，三种可观测性数据分别看什么？

**参考答案**：日志记录具体事件和上下文，指标用于聚合趋势和告警，Trace 把一次请求跨服务、数据库和模型调用串成时间线。三者应共享请求 ID、租户 ID 的不可敏感版本或 trace ID，但不应把完整用户隐私和密钥塞进每条记录。

Agent 服务还可以记录首 token 延迟、工具调用次数、重试、token 消耗、检索命中和人工转接率。指标告诉你问题是否扩大，Trace 帮你定位阶段，日志提供具体错误；缺少任何一类都会增加排查时间。

### 18. 错误处理应该如何分层？

**面试问法**：异常是应该在底层捕获还是一路抛到接口层？

**参考答案**：底层只在能够恢复或补充上下文时捕获异常，例如把驱动错误转换成领域错误并保留异常链；上层根据调用场景决定重试、降级、返回状态码或触发告警。不要在每层重复记录同一堆栈，也不要把所有异常转换成“系统繁忙”。

错误响应应区分可由用户修正的参数问题、可重试的暂时性故障、权限问题和不可恢复的内部错误。Agent 工具失败还要把安全、结构化的错误信息交给编排器，而不是把内部堆栈原样暴露给模型或用户。

### 19. 什么是技术债？如何管理？

**面试问法**：技术债是不是所有“不优雅”的代码？

**参考答案**：技术债是为了短期速度而承担的未来维护成本，可能来自临时方案、缺少测试、过时依赖、错误的边界或没有记录的设计决策。它不是单纯的个人审美问题，而是会让变更更慢、故障更多或风险更高的可观察成本。

管理技术债要描述影响、评估偿还收益、安排负责人和验收标准。可以在重构同一模块、修复故障或升级依赖时顺手偿还一部分，避免把“以后再做”当成无限期的计划。

### 20. 重构和重写有什么区别？

**面试问法**：什么时候应该重写系统？

**参考答案**：重构是在保持外部行为基本不变的前提下改善内部结构，通常通过小步提交、测试和逐步迁移完成；重写是重新实现系统，可能同时改变数据模型、接口和运行方式，风险与验证成本更高。

重写只有在现有架构无法通过渐进改造满足关键约束时才值得考虑。即使决定重写，也应采用双写、影子流量、分阶段切换和可回滚方案，而不是把所有风险集中到一次发布。

### 21. 如何做数据库或接口的兼容迁移？

**面试问法**：字段要改名，如何让新旧版本同时运行？

**参考答案**：常用扩展、迁移、收缩流程：先增加新字段或新接口，旧代码仍可运行；应用在过渡期双读或双写并校验差异；确认所有实例和消费者升级后，再停止旧路径并清理旧字段。每一步都要有回滚或补偿计划。

接口和消息格式也要遵守向后兼容，新增字段通常比删除或改变含义安全。迁移脚本应可重复、可观测、可限速，避免一次性锁住大表或让双写失败时静默丢数据。

### 22. AI 生成代码最容易出现什么工程问题？

**面试问法**：你如何 Review 一段 AI 生成的代码？

**参考答案**：我会重点检查它是否真的理解业务边界，尤其是异常吞掉、默认超时缺失、重试非幂等、共享状态污染、权限检查遗漏、资源没有释放和日志泄露。还要核对依赖版本、API 是否真实存在，以及代码是否只在理想输入下工作。

Review 不应停留在“看起来合理”，要用测试、类型检查、静态扫描和小规模运行验证。对 Agent 代码，还要检查模型输出是否被当作可信指令、工具参数是否重新校验、上下文是否可能跨租户串联。

### 23. 如何制定 AI 生成代码的验收标准？

**面试问法**：AI 写的代码怎样才能进入主分支？

**参考答案**：先把验收标准写成可观察行为，包括输入输出、错误码、性能预算、安全边界、日志字段和兼容性，再要求 AI 生成实现和测试。生成代码必须通过格式、类型、单元测试、集成测试和人工 Review，关键模块还要做故障注入或安全检查。

验收标准应关注结果而非代码是否“像人写的”。如果一段实现满足契约、可维护且风险可控，就可以接受；如果只是通过了几个样例，却无法解释失败路径，就不能因为生成速度快而降低门槛。

### 24. 线上事故复盘应该怎么做？

**面试问法**：复盘是找谁犯错吗？

**参考答案**：高质量复盘关注时间线、影响范围、检测和响应过程、根因与促成条件，以及哪些系统性措施可以降低复发概率。要区分直接触发因素和长期积累的脆弱点，例如缺少超时、监控盲区、发布流程没有回滚。

行动项必须有负责人、截止时间和验收证据，优先修复能阻断事故扩大的护栏。复盘不应把问题归咎于某个人的粗心，否则团队会隐藏风险，系统也不会真正变得更可靠。

### 25. 如何判断一个工程改动是否值得做？

**面试问法**：面对很多优化和重构建议，你如何排序？

**参考答案**：我会先看用户影响、故障风险、成本、交付时间和可逆性，再看是否有数据证明问题存在。能显著降低事故概率、延迟或成本的改动通常优先；只改善局部代码观感、却没有明确收益的改动可以延后。

对于 Agent，应该把质量、成本、延迟和人工兜底一起评估。例如把模型换成更大的版本可能提高回答质量，却也增加费用和延迟；先通过检索质量、提示词、缓存和路由实验确认瓶颈，再决定是否升级模型。
