# 15.7 系统设计

> 本节用 25 道场景题训练系统设计表达。每题都按“先澄清目标，再拆分核心链路，最后说明取舍和故障边界”的方式回答。系统设计没有唯一答案，关键是能把需求、容量、可靠性、成本和验证方法连起来。

## 一、系统设计通用方法

### 1. 系统设计题应该从哪里开始？

**面试问法**：面试官说“设计一个智能客服”，你第一分钟说什么？

**参考答案**：先澄清用户、核心流程、QPS、延迟、数据规模、可用性、合规和成本目标，明确本次设计不覆盖什么。然后画出客户端、网关、业务服务、模型、工具、存储和异步任务的边界，再挑一条关键请求链路深入。

不要一上来罗列 Kafka、Redis 和 Kubernetes。技术选型必须服务于约束，面试官更想看到你如何从目标推导架构，以及在规模、成本和复杂度之间做取舍。

### 2. 如何做容量估算？

**面试问法**：一天一百万次请求，大概需要多少 QPS 和存储？

**参考答案**：先把日请求量除以全天秒数得到平均 QPS，再根据业务峰值倍数估算峰值 QPS。存储要乘以单条数据大小、保留天数、复制和索引放大；带宽则要结合请求和响应平均大小、峰值并发和压缩比例。

估算不必一开始非常精确，但要写出假设并说明如何用监控修正。Agent 还要把模型调用次数、平均输入输出 token、并发连接和流式持续时间纳入容量，否则只估 HTTP 请求数会严重低估成本和资源。

### 3. 如何设计一个多轮对话服务？

**面试问法**：用户发消息后，服务端如何保存和生成回复？

**参考答案**：入口层做鉴权、限流和请求校验，应用层创建消息和运行记录，编排器读取经过权限过滤的上下文，调用模型和工具，并把事件流写入持久化存储。响应可以通过 SSE 或 WebSocket 流式返回，后台任务负责摘要、计费和评估等非关键路径。

会话状态不能只放在单个进程内存中，否则重启、扩容和重试都会丢失。每次运行应有唯一 run ID 和幂等键，消息、工具调用、模型输出和错误都能关联和重放。

### 4. 如何设计 Agent 流式输出？

**面试问法**：模型 token 生成过程中，怎样让前端实时看到？

**参考答案**：模型客户端把增量事件交给编排器，编排器过滤和规范化后通过 SSE 或 WebSocket 发送给前端，同时按事件或批次写入运行日志。事件需要包含顺序号、类型、run ID 和结束标记，客户端断线后应能判断是正常结束、可恢复还是失败。

链路要关闭代理缓冲并设置心跳和空闲超时，服务端要限制队列和响应大小。持久化与实时发送之间要处理顺序和重复，重连时可以按最后事件 ID 补发，或者明确告诉客户端该次运行只能重新开始。

### 5. 如何设计一个 RAG 问答系统？

**面试问法**：从上传文档到回答，完整链路怎么拆？

**参考答案**：文档进入后先做解析、分块、元数据提取和权限标记，再生成 embedding 写入向量索引，同时保存原文、版本和处理状态。查询侧先做身份和租户过滤，再进行关键词、向量或混合召回，重排后把带来源的片段交给模型生成回答。

系统要能追溯回答使用了哪些文档和版本，并在文档删除、权限变更和索引失败时保持一致。评估不能只看模型回答流畅度，还要测召回率、引用正确性、拒答、延迟和成本。

### 6. 如何设计工具调用平台？

**面试问法**：多个 Agent 共用工具时，怎么保证安全和稳定？

**参考答案**：工具注册中心保存名称、版本、输入 schema、权限、超时和资源配额，执行层统一做参数校验、鉴权、限流、审计和结果标准化。同步工具适合短请求，长任务进入队列并返回任务 ID，结果通过事件或查询接口获取。

工具必须有幂等策略和明确错误分类，不能让模型直接决定数据库连接、文件路径或网络目标。执行环境应按风险分级，必要时使用独立容器、只读挂载、网络白名单和进程限制。

### 7. 如何设计异步任务编排系统？

**面试问法**：文档解析、批量评测和长时间工具调用如何处理？

**参考答案**：API 只负责创建任务和返回 task ID，任务表保存状态、参数版本、进度、重试次数和错误；消息队列负责投递，Worker 执行具体步骤，结果写入持久化存储。状态更新要使用幂等条件，避免重复消费把任务推进两次。

任务需要超时、取消、重试和死信处理。调度器应限制每租户和每类任务的并发，Worker 崩溃后可以依据租约或心跳恢复；对于不可重试的业务错误要终止并给出可行动的原因。

### 8. 如何设计模型路由和降级？

**面试问法**：主模型超时或限流时，系统怎么办？

**参考答案**：路由层根据任务类型、质量要求、上下文长度、区域和成本选择模型，记录每次选择的原因和版本。主模型失败时，可以在总截止时间内切换到备用模型、缓存答案、规则回复或人工队列，但要区分限流、认证、内容拒答和参数错误。

降级不能无限重试或无条件切换更贵模型。应设置每次请求的总预算、最大重试次数和质量阈值，对不同租户和任务配置允许的备用路径，并用评估数据验证降级后的可接受程度。

### 9. 如何设计上下文和记忆管理？

**面试问法**：对话很长时，如何控制 token 又不丢重要信息？

**参考答案**：把当前消息、系统约束、工具结果、长期偏好和历史摘要分层管理。进入模型前按优先级、来源和 token 预算选择内容，必要时先摘要再截断；摘要和重要事实应保留来源、版本和可撤销能力。

上下文构建要可观测，记录被保留、压缩和淘汰的原因。不能只按字符长度截断，否则可能丢失权限、任务约束或工具结果；也不能把未经确认的模型推断永久写入长期记忆。

### 10. 如何设计多租户 Agent 平台？

**面试问法**：不同客户共享服务和模型资源，怎么隔离？

**参考答案**：认证层确定租户和用户身份，策略层决定可用模型、工具、数据集和预算，数据层在会话、文档、向量、缓存和对象存储中统一带租户边界。资源层按租户设置并发、速率、token 和存储配额，防止一个客户耗尽共享资源。

管理员操作、模型调用和工具执行都要审计。共享基础设施可以降低成本，但高敏感租户可能需要独立密钥、独立索引或独立实例，取舍应由合规和容量目标驱动。

## 二、可靠性与性能场景

### 11. 如何设计限流系统？

**面试问法**：模型 API 和工具调用如何防止被打爆？

**参考答案**：先确定限流维度，例如租户、用户、API Key、模型和工具，再选择固定窗口、滑动窗口、令牌桶或漏桶。令牌桶适合允许一定突发并控制长期平均速率，计数器和配额表可以落在 Redis 或网关层。

限流响应要让客户端知道何时重试，并与队列、连接池和并发上限配合。仅限制请求次数可能无法控制模型成本，Agent 还要按 token、工具耗时或任务权重进行预算。

### 12. 如何设计熔断和降级？

**面试问法**：下游模型持续超时时，服务如何保护自己？

**参考答案**：熔断器在错误率、超时率或并发等待超过阈值时快速失败，避免继续占用连接和线程；经过冷却时间后以少量探测请求进入半开状态，成功才逐步恢复。降级可以返回缓存、简化答案、异步任务或人工处理。

阈值要按下游和业务分组，不能一个全局开关让所有功能同时失效。错误分类很重要，参数错误和权限错误不应被当成暂时性故障重试。

### 13. 如何设计幂等和重试？

**面试问法**：客户端超时后重发请求，如何避免重复执行工具？

**参考答案**：客户端为一次业务操作生成幂等键，服务端持久化请求状态和结果，重复请求返回已有结果或当前处理中状态。工具执行前检查幂等记录，执行后以事务或原子状态更新标记完成。

重试要有总截止时间、指数退避和抖动，只针对可恢复错误；非幂等动作必须先补齐幂等能力，或者通过人工确认和补偿流程执行。不能只在 HTTP 客户端里配置三次重试就认为业务安全。

### 14. 如何设计可观测的 Agent 平台？

**面试问法**：一次回答质量下降，如何知道是检索、模型还是工具问题？

**参考答案**：每次请求生成 trace ID 和 run ID，把网关、编排、检索、重排、模型、工具和数据库调用串成 Trace。指标记录成功率、首 token 延迟、总耗时、token、工具错误、检索命中和人工转接，日志记录结构化事件和关键输入摘要。

观测数据要注意隐私和成本，原文、提示词和模型输出可以按采样、脱敏和权限分级保存。通过固定评测集、线上抽样和用户反馈，把技术指标与回答正确性联系起来，避免只优化延迟而质量下降。

### 15. 如何设计 Agent 成本控制？

**面试问法**：如何避免一个请求无限调用模型和工具？

**参考答案**：在请求入口、编排循环和租户层设置 token、时间、工具次数和费用预算，每次调用前预估剩余预算，超出时提前停止、摘要、降级或转人工。模型路由可按任务使用不同价格和能力的模型，缓存确定性结果，批量处理离线任务。

成本记录必须能归因到租户、用户、会话、模型和工具，并与质量指标一起分析。不能只在月底看账单，应该对异常增长设置实时告警和自动限额。

### 16. 如何设计知识库导入和增量更新？

**面试问法**：企业文档不断变化，如何保证检索到的内容是新版本？

**参考答案**：导入任务先记录文档版本和内容哈希，再异步解析、分块、embedding 和索引。索引状态要区分待处理、成功、失败和过期，查询时只使用已发布且有权限的版本。新版本完成验证后再切换为当前版本，避免半成品被检索。

删除和权限变更也要进入同一状态机，清理缓存和向量索引。任务必须可重试、可恢复，失败文档要有人工重跑和错误报告，不应因为一个大文件失败而阻塞整批导入。

### 17. 如何设计文件上传和多模态处理？

**面试问法**：用户上传 PDF、图片和表格后，如何进入 Agent？

**参考答案**：文件先上传到对象存储，服务端校验大小、类型、病毒和租户权限，再创建异步处理任务。解析器按类型提取文本、表格、图片和元数据，产物保存版本和来源，最终进入检索或模型处理链路。

不能让模型服务直接访问任意用户提供的 URL 或本地路径。处理过程要设置资源上限、超时和隔离，结果引用原文件版本，下载时再次校验权限和短期签名。

### 18. 如何设计实时协作或长连接场景？

**面试问法**：多人同时查看 Agent 运行状态，怎样保证看到的事件顺序一致？

**参考答案**：运行状态以事件流或版本号为准，服务端给每个事件分配单调序号，客户端根据序号去重、补洞和重连。长连接网关负责连接管理，状态和事件存储在共享层，不能只放在某一台实例内存。

需要双向交互时使用 WebSocket，需要单向进度推送时 SSE 更简单。系统要处理连接迁移、心跳、空闲回收、权限变化和慢客户端背压，避免一个客户端拖住事件生产。

### 19. 如何做高可用和故障转移？

**面试问法**：模型、数据库或某个服务实例挂了，系统怎么继续？

**参考答案**：先定义可用性目标和允许丢失的数据，再按依赖设置多实例、健康检查、超时、重试、熔断和备用区域。无状态 API 可以横向扩展，有状态会话和任务需要共享存储、复制或可恢复检查点。

故障转移不能只写在架构图上，要通过演练验证 DNS、连接池、复制延迟、任务重试和回滚。每个备用路径都有成本和新的故障模式，应该只为关键目标建设。

### 20. 如何从单体演进到服务化？

**面试问法**：什么时候值得拆微服务？

**参考答案**：当模块有独立扩缩容、发布节奏、权限边界或故障隔离需求，并且团队有能力承担分布式调用、观测和运维成本时，再考虑拆分。优先按稳定业务边界提取模块，通过内部接口或消息解耦，而不是按数据库表或技术名词切服务。

演进可以先模块化单体、建立契约和可观测性，再逐步抽出高负载或高风险模块。微服务不是性能优化的默认答案，过早拆分会增加网络、事务、一致性和发布复杂度。

## 三、综合场景题

### 21. 如何设计一个 Agent 评测平台？

**面试问法**：如何比较两个 Prompt、模型或工作流版本？

**参考答案**：评测平台保存数据集版本、输入、期望标准、运行配置和完整 Trace，执行器批量调用 Agent 并记录回答、工具轨迹、token、延迟和错误。评分可以结合规则、引用匹配、模型评审和人工标注，但要保留原始证据。

发布前看离线回归，发布后看线上抽样、用户反馈和成本变化。数据集、评分器和模型版本都要可追溯，避免“分数变了但不知道是题目、评分器还是实现变了”。

### 22. 如何设计工具执行沙箱？

**面试问法**：允许 Agent 执行代码或命令时，系统边界怎么划？

**参考答案**：控制面负责任务、权限和审计，执行面在短生命周期隔离环境中运行，使用最小权限、只读挂载、网络白名单、CPU/内存/时间/进程数限制和系统调用过滤。输入输出通过受控通道传递，结果和日志按任务 ID 保存。

沙箱要防止路径穿越、符号链接、环境变量泄露、元数据服务访问和资源耗尽。风险高的代码可以放入独立节点或微虚拟机，不能只依赖容器内的应用校验。

### 23. 如何设计一个模型网关？

**面试问法**：多个模型供应商统一接入，需要哪些能力？

**参考答案**：网关统一认证、路由、请求 schema、超时、流式协议、错误模型、重试和计费埋点，对外暴露稳定接口，对内适配不同供应商。模型、区域、版本和能力应通过配置或策略选择，而不是散落在业务代码中。

网关要处理供应商限流、响应格式差异、内容安全和数据驻留要求。对故障切换要保留请求幂等和总预算，不能因为备用模型协议不同而让业务收到无法解析的结果。

### 24. 如何设计一个通知系统？

**面试问法**：Agent 任务完成后，通过站内信、邮件和短信通知用户，怎么做？

**参考答案**：业务服务写入通知事件或 Outbox，异步消费者根据用户偏好和模板分发到不同渠道。每个渠道有独立重试、限流、死信和供应商适配，通知记录保存状态、尝试次数和供应商响应。

Outbox 让业务事务和事件写入保持一致，消费者通过幂等键避免重复发送。系统还要支持取消、退订、模板版本、敏感信息脱敏和高峰期优先级。

### 25. 系统设计题如何讲清取舍？

**面试问法**：面试官追问“为什么不用另一个方案”，你怎么答？

**参考答案**：先回到需求和约束，再说明候选方案在延迟、成本、一致性、复杂度、团队能力和故障恢复上的差异，最后给出当前阶段的选择和未来演进条件。例如低并发内部工具可以先用关系库任务表，不必一开始引入复杂消息平台；当任务量和隔离需求达到阈值，再迁移到队列集群。

好的回答还要说验证方式：用容量测试验证吞吐，用故障演练验证恢复，用评测集验证质量，用账单和指标验证成本。系统设计不是堆组件，而是把选择、风险和证据串成一个可执行的方案。
