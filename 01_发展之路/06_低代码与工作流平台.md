# 1.6 低代码与工作流平台：把常见步骤组合成应用

做活动报名时，可以用现成表单收集信息，用表格汇总，再给报名者发送通知。很多环节无需重新开发，只要把已有能力连接好。低代码与可视化工作流采用的就是这种思路。

它们不是在编码智能体之后才出现的“下一代技术”，而是与代码开发长期并行的一类工具。引入大模型后，流程中可以增加文本分类、内容生成、资料检索等步骤。

## 先区分两类看起来相似的产品

第一类让你在画布上连接节点。例如输入用户问题，检索资料，调用模型，最后输出回答。你主要维护流程和节点配置。

第二类根据自然语言生成应用代码，并提供预览。你主要检查生成的页面、数据操作和代码结构。虽然两类产品都能降低初次制作的门槛，交付与维护方式却不一样。

| 观察角度 | 可视化工作流 | 应用生成工具 |
| :--- | :--- | :--- |
| 主要编辑对象 | 节点、连接和条件 | 页面与应用代码 |
| 常见产出 | 问答应用、自动化流程、接口 | 可交互的应用原型或项目 |
| 后续修改 | 调整流程、参数和数据来源 | 继续生成或直接修改代码 |
| 需要核对 | 分支、权限、失败处理 | 功能完整性、数据保存、部署条件 |

## 一个知识问答流程怎样搭起来

以“查询活动报名规则”为例，可以先设计一条较短的流程：接收问题，查找相关规则，把资料和问题一起交给模型，最后显示回答与出处。

只看正常问题，这条流程很容易演示成功。要让它能持续使用，还应明确：没有找到规则时怎么回答，两份规则日期冲突时用哪份，上传新规则后旧版本如何处理，查询失败时页面显示什么。

这些判断不会因为节点能拖拽就自动消失。平台主要帮你省去连接组件和搭建界面的部分工作，业务规则仍然需要设计。

## 常见平台与阅读入口

### 可视化流程与应用编排

- [Dify](https://dify.ai) 与其[开源仓库](https://github.com/langgenius/dify)：可从知识库问答和工作流入手，后续章节会继续实践。
- [Coze（扣子）](https://www.coze.cn)：了解智能体、插件与工作流，具体能力以对应站点版本为准。
- [Langflow](https://www.langflow.org) 和 [Flowise](https://flowiseai.com)：了解可视化组件组合与模型应用开发。

使用时要查看项目的导出形式。导出流程配置并不必然等于导出独立可运行的源码；有些流程仍依赖平台的运行服务和插件。

### 通过描述生成应用

- [Bolt](https://bolt.new)：查看浏览器中的应用开发与预览方式。
- [Lovable](https://lovable.dev)：了解从描述到应用的制作过程。
- [v0](https://v0.app)：了解界面与应用生成能力。

生成页面之后，要实际操作创建、修改、删除和刷新。列表里出现了示例数据，不等于已经连接数据库；登录框能输入文字，也不等于已经完成身份验证。

## 什么情况下值得写代码

若流程主要由常见组件构成，平台可以帮助快速验证想法。若出现复杂事务、特殊数据格式、性能瓶颈或平台没有的接口，就可能需要增加代码节点，或者把这部分放到独立服务中。

不必因为遇到一个平台不支持的功能，就推翻全部流程。可以先确定边界：平台负责组织问答，独立服务负责订单查询，页面负责交互。各部分通过明确的接口连接。

反过来，如果为了一个简单流程写了大量底层连接代码，也可以考虑已有工具是否足够。选择时看维护成本和业务约束，不需要把“代码越多”当作能力证明。

## 从演示到可交付，需要再走哪些步骤

1. 用真实且经过脱敏的输入验证，避免只用精心挑选的样例。
2. 检查空输入、错误输入和外部服务超时，确认流程有明确出口。
3. 记录模型、提示词、数据版本及关键配置，方便复现结果。
4. 明确数据存放位置、访问权限与费用来源。
5. 让另一位使用者按说明完成一次操作，检查说明是否足够。

例如活动规则更新后，应重新测试“截止时间”“退款条件”等关键问题。只确认画布上没有报错，无法发现回答引用了旧规则。

低代码平台与编码智能体可以结合使用：先验证流程，再按需要开发扩展。但是否节省时间，要把调试、部署和后续维护一起计算，不能只看首次生成页面花了几分钟。
