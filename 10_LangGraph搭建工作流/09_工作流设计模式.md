# 09 工作流设计模式：先选型，再动手

学完前九节，你手里的工具箱已经很满了：状态图、条件路由、Send 并行、工具循环……但真接到需求时，新手最容易犯的错误是**上来就堆代码**，画了一张 20 个节点的巨图，最后发现三行 `if/else` 就够了。

LangGraph 官方在《Workflows and agents》里总结了一套设计模式菜单。这一节我们把它们对号入座——你会发现前面各节早已把这些模式“偷偷”练过了，现在只需要把名字和适用场景钉牢。

## 1. 先分清：Workflow 与 Agent 是两种生物

官方的区分标准只有一条：**路径是写死的，还是模型自己定的？**

- **Workflow（工作流）**：开发者预先用代码写死每一步流程，大模型只是流程中的“工人”。像中央厨房的标准化流水线：洗菜 → 切菜 → 炒菜 → 装盘，顺序永远不变。
- **Agent（智能体）**：大模型自己决定下一步干什么、调用什么工具、什么时候结束。像交给大厨一句“做一桌好菜”，怎么安排他自己看着办。

**选型口诀**：流程越确定越要 Workflow（可控、便宜、好调试）；任务越开放才越要 Agent（灵活但费 Token、易跑偏）。很多生产系统是“外壳 Workflow、内芯 Agent”——大框架写死，关键决策点才交给模型。

## 2. 五大模式速查表

| 模式 | 一句话 | 生活化比喻 | 前面哪节练过 |
| :--- | :--- | :--- | :--- |
| Prompt Chaining（提示链） | A 的输出接给 B，B 的输出接给 C | 翻译稿先直译、再润色、最后校对 | 02 节的多节点串联 |
| Routing（路由） | 先分类，再按类别走不同分支 | 医院分诊台 | 03 节条件路由 |
| Parallelization（并行） | 多个独立子任务同时开工 | 多灶台同时炒菜 | 04 节 Fan-out/Fan-in |
| Orchestrator-Worker（编排者-工人） | 主管先拆任务，动态派给 N 个工人，最后汇总 | 项目经理拆需求派活，再收总 | 04 节 Send（Map-Reduce） |
| Evaluator-Optimizer（评估者-优化者） | 生成器写稿，评估器打分，不合格打回重写 | 作家与编辑的“改稿拉锯战” | 03 节决策树 |
| Agent（工具循环） | 模型自己决定用哪个工具、何时收工 | 只动嘴的老专家 + 跑腿助理 | 08 节工具调用循环 |

## 3. 三个最值得展开的模式

### 3.1 Orchestrator-Worker：动态数量的“派活”

它与普通 Parallelization 的区别在于：**工人数量运行时才知道**。比如“帮我把这篇文章摘要翻译成 5 种语言”——翻译成几种？读文档才知道。这正是 04 节 `Send` 的标准用法，官方文档在 Orchestrator-Worker 一节推荐的正是 Send API：

```python
def orchestrator(state: State):
    """主管：先拆任务（LLM 产出 langs 列表），再动态派发"""
    return [Send("translate", {"lang": l, "text": state["text"]}) for l in state["langs"]]
```

### 3.2 Evaluator-Optimizer：改稿拉锯战

两个角色、一条回路：Generator（写手）生成内容，Evaluator（编辑）用结构化输出打分，不合格就带批注重写。这个模式的两个关键保险丝别忘装：

```python
# 1. 评估器输出必须是结构化的（打分 + 批注），路由函数只读字段
class Feedback(BaseModel):
    grade: Literal["ok", "needs_improvement"]
    comment: str

# 2. 兜底防死循环：重写超过 N 次强制放行
def route_after_eval(state: State) -> Literal["rewrite", "pass", "force_pass"]:
    if state["revision"] >= 3:
        return "force_pass"
    return "rewrite" if state["feedback"].grade == "needs_improvement" else "pass"
```

### 3.3 Routing：最容易被低估的模式

Routing 看似简单，却是生产系统里**性价比之王**：大部分用户请求其实不需要重型 Agent，一个廉价的分类调用就能把 80% 的流量分给轻量分支，只有复杂请求才进大循环。16 节旅行助手的主助理本质就是一个 Routing 模式：用“转交工具”把意图分给四个子助理。

## 4. 决策清单：动手前先问四个问题

1. **步骤是固定的吗？** 固定 → Prompt Chaining / Routing / Parallelization；
2. **子任务数量运行时才知道吗？** 是 → Orchestrator-Worker（Send）；
3. **质量需要反复打磨吗？** 是 → Evaluator-Optimizer（记得设重写上限）;
4. **连“下一步干什么”都要模型自己定吗？** 是 → Agent（工具循环）。

四个问题都答“否”，也许你根本不需要 LangGraph——一段普通 Python 函数更便宜更稳。这也是一种成熟。
