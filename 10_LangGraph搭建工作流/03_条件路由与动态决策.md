# 03 条件路由与动态决策

在上一节中，我们通过 `add_conditional_edges` 实现了一个简单的“十字路口”：大模型想调用工具就去工具节点，否则就结束。但在真实业务里，工作流的岔路口远比这复杂——有时要根据用户意图分成三四个分支，有时需要让大模型像“路由裁判”一样决定下一步去哪。

LangGraph 官方对这张图的定义非常精炼：**节点负责干活（nodes do the work），边负责决定下一步去哪（edges tell what to do next）**。条件路由，就是那张最关键的“指路牌”。

## 1. 条件路由的本质：一个函数 + 一张路径表

条件路由其实非常简单，它只有两个要素：

1. **路由函数（Routing Function）**：一个普通的 Python 函数，读一下当前 `State`，然后返回一个“目的地名字符串”。
2. **路径表（Path Map，可选）**：一个字典，负责把路由函数返回的字符串，翻译成图中真实存在的节点名。

```python
from langgraph.graph import StateGraph, START, END

def route_logic(state: State) -> str:
    """看一眼前面的对话，决定下一步去哪"""
    last_message = state["messages"][-1]
    if last_message.tool_calls:
        return "call_tool"      # 返回值：逻辑上的名字
    return "finish"             # 返回值：逻辑上的名字

builder.add_conditional_edges(
    "assistant",                # 从哪个节点出发
    route_logic,                # 路由函数
    {
        "call_tool": "tools",   # 路径表：逻辑名 -> 真实节点名
        "finish": END,
    },
)
```

> 💡 **为什么要有“路径表”？** 因为路由函数常常是从 LLM 返回的字符串里“翻译”来的，而 LLM 可能返回各种五花八门的措辞。路径表相当于一个“同义词过滤器”，把不稳定的逻辑返回值映射到稳定的节点名上。如果省略路径表，LangGraph 会直接把路由函数的返回值当作节点名去图中查找。

## 2. 给路由函数加上“紧箍咒”：Literal 类型约束

社区教程里最推荐的一个小技巧：用 `typing.Literal` 给路由函数的返回值加上类型约束。这样在 IDE 里写错节点名，静态检查（mypy/Pyright）会当场标红，而不是等到运行时才炸。

```python
from typing import Literal

def route_logic(state: State) -> Literal["search_node", "answer_node"]:
    """返回值只能是这两个名字之一"""
    if state.get("needs_search"):
        return "search_node"
    return "answer_node"
```

> ⚠️ `Literal` 只在**静态类型检查**时起作用，不影响运行时行为。它相当于给“指路牌”加了一道出厂质检，但真正执行时仍以返回值字符串为准。

## 3. 三岔路口：一个节点分出多个分支

条件边最常用的场景，就是“意图识别 + 分发”。比如我们做一个“内容审校工作流”，模型需要判断用户输入属于哪一类，然后路由到不同的处理节点：

代码实现（完整可运行：配上你自己的模型 Key，直接 `python demo.py` 即可）：

```python
from typing import TypedDict
from langchain_openai import ChatOpenAI
from langgraph.graph import StateGraph, START, END

class State(TypedDict):
    input: str          # 用户原始输入
    category: str       # 分诊结果

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

def classify(state: State):
    """分诊台：让大模型对用户输入做意图分类，把结果写进 State"""
    response = llm.invoke(
        f"请判断这句话的意图，只能回答 review / translate / summarize / chat 之一：{state['input']}"
    )
    return {"category": response.content.strip().lower()}

def handle(state: State):
    """各科室：这里用同一个函数占位，真实项目里各写各的处理逻辑"""
    return {"input": f"[{state['category']}] 已处理：{state['input']}"}

builder = StateGraph(State)
builder.add_node("classify", classify)
builder.add_node("review_node", handle)
builder.add_node("translate_node", handle)
builder.add_node("summarize_node", handle)
builder.add_node("chat_node", handle)
builder.add_edge(START, "classify")
for name in ["review", "translate", "summarize", "chat"]:
    builder.add_edge(f"{name}_node", END)

# 注意：路由函数读的是 State 里算好的 category 字段（进阶实践：决策与路由分离）
builder.add_conditional_edges(
    "classify",
    lambda state: state["category"],
    {
        "review": "review_node",
        "translate": "translate_node",
        "summarize": "summarize_node",
        "chat": "chat_node",
    },
)

graph = builder.compile()
print(graph.invoke({"input": "帮我把这段话翻成英文：你好，世界"}))
```

**生活化比喻：** 这就像医院的分诊台。护士（分类节点）听完病人描述，判断是“发烧去内科”“骨折去骨科”“牙疼去口腔科”，然后一指路，病人就走向对应的科室。没有分诊台，所有病人都挤在一个医生那，必然乱套。

## 4. 决策树：让大模型当“路由裁判”

有些时候，路由的规则写死在 Python 里太僵硬。比如“这个回答够不够好？要不要重写一次？”，这类判断本质上需要大模型的语义理解，而不是简单的 `if/else`。

LangGraph 官方的推荐模式，就是让 LLM 输出一个结构化的小分类（比如只允许输出 `yes` / `no`），路由函数再读这个结果：

```python
from pydantic import BaseModel, Field

class GradeAnswer(BaseModel):
    """判断回答是否已经解决用户问题"""
    binary_score: str = Field(
        description="回答已解决问题，返回 'yes'，否则返回 'no'"
    )

# 让大模型只输出一个分数，当"裁判"
grader = llm.with_structured_output(GradeAnswer)

def decide_retry(state: State) -> str:
    """裁判：回答不合格，就回到生成节点重写一遍"""
    result = grader.invoke(state["messages"])
    return "rewrite" if result.binary_score == "no" else END
```

这样，我们就构建出了一棵**决策树**：不合格就重写，合格就结束，而重写次数由 `recursion_limit` 兜底控制，防止无限循环。

> 🔧 **进阶实践**（官方与社区都推荐）：当分支逻辑复杂（3 条以上）时，不要把所有判断都堆在路由函数里。更好的做法是——先让一个普通节点把“决策结果”算好并写进 `State` 的某个字段，再让路由函数只做一个“读字段、返回节点名”的瘦函数。这样决策逻辑可以单独单测，调试时也能用流式输出直接看到决策字段。

## 5. 一个条件边可以指向“多个目的地”吗？

可以。`add_conditional_edges` 的路由函数除了返回单个字符串，还可以返回一个**字符串列表**。此时 LangGraph 会走“并行分发”：同时向列表里的所有节点发出指令。

```python
def fan_out_route(state: State) -> list[str]:
    """需要同时做多件事，比如既查航班又查酒店"""
    return ["search_flights", "search_hotels"]

builder.add_conditional_edges(
    "planner",
    fan_out_route,
    ["search_flights", "search_hotels"],
)
```

这就是下一节要讲的“并行执行”的入口。**条件路由负责“分岔”，并行节点负责“同时跑”**，两者往往配合使用。

## 6. 进阶：Command API（1.x 动态跳转的另一种写法）

LangGraph 1.x 还提供了 `Command`，让一个节点在**返回状态更新的同时**直接声明“下一步去哪”（`goto`），相当于把“节点返回”和“路由”合并成一步：

```python
from langgraph.types import Command

def smart_node(state: State) -> Command:
    """既更新状态，又指定下一步"""
    decision = decide_next(state)
    return Command(goto="next_node", update={"last_decision": decision})
```

`Command` 与条件边的取舍：能用 `add_conditional_edges` 表达的就别用 `Command`（图更直白、更好可视化）；只有当节点想“改状态 + 跳转”一起干，或需要跳转到父图/子图里的节点时，才用 `Command`。

## 7. 常见坑与最佳实践

- **路由函数返回了不存在的节点**：会抛出 `ValueError`（运行时可能包装成 `GraphRuntimeError`），图立即终止。排查时确认路径表所有目标都 `add_node` 过，`END`/`START` 正确导入。
- **路由函数里别改 State**：路由函数应保持“只读 + 纯函数”，不要在它内部写状态，否则容易和 reducer 产生意料之外的冲突。
- **给路由函数加 `Literal` 类型标注**：让 IDE 和静态检查帮你提前发现拼写错误。
- **用可视化验证**：`print(app.get_graph().draw_mermaid())` 一眼看清每条条件边连到哪（第五节细讲）。
