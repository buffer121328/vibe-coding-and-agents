# 08 工具调用循环与预构建组件

前七节我们一直在画“轨道图”，但有一条所有 Agent 共用的核心闭环始终没有正式讲透——**工具调用循环（Agent Loop）**。它是所有 Agent 的心脏，也是从“入门画图”到“实战搭 Agent”之间最大的那道断层；16 节综合实战里反复出现的 `ToolNode`、`tools_condition`、`create_tool_node_with_fallback`，全是围绕它搭建的。

## 1. 什么是工具调用循环？

**生活化比喻：** 大模型就像一位“只动嘴不动手的老专家”。他博览群书、思路清晰，但既不能上网查票，也不能操作数据库。他每说一句话，旁边都要跟着一位“跑腿助理”（ToolNode）：专家写张字条说“帮我查一下明天飞东京的航班”，助理跑一趟把结果抄在便签上递回去，专家看完便签再决定是继续查，还是给出最终答案。这一来一回，就是一个循环。

在 LangGraph 里，这个循环的标准画法只有三步：

```python
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool
from langgraph.graph import StateGraph, MessagesState, START
from langgraph.prebuilt import ToolNode, tools_condition

@tool
def search_flights(destination: str) -> str:
    """查询指定目的地的航班"""
    return f"{destination} 有 3 个航班"

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0).bind_tools([search_flights])

def call_model(state: MessagesState):
    """专家节点：模型收到的是整个 State，所以包一层只把消息列表喂给它"""
    return {"messages": [llm.invoke(state["messages"])]}

builder = StateGraph(MessagesState)
builder.add_node("assistant", call_model)               # 1. 专家节点
builder.add_node("tools", ToolNode([search_flights]))   # 2. 跑腿助理节点
builder.add_edge(START, "assistant")
builder.add_conditional_edges("assistant", tools_condition)  # 3. 指路牌
builder.add_edge("tools", "assistant")                  # 结果递回去，形成闭环

graph = builder.compile()
```

这个 `模型 → 工具 → 模型` 的反复循环，就是业界常说的 **ReAct（Reason + Act）模式**——想一步、做一步、看结果、再想下一步。LangGraph 的循环图（Cyclic Graph）能力在这里发挥得淋漓尽致。

## 2. 三块核心积木：bind_tools / ToolNode / tools_condition

| 积木 | 干什么的 | 生活化比喻 |
| :--- | :--- | :--- |
| `llm.bind_tools([...])` | 告诉大模型“你有哪些工具可点”，输出 `tool_calls` | 给专家一张菜单，他只能点菜单上的菜 |
| `ToolNode(tools)` | 接收 `tool_calls`，真正执行 Python 函数，结果包成 `ToolMessage` | 跑腿助理：接单、干活、交回执 |
| `tools_condition` | 看模型最后一条消息有没有 `tool_calls`，有就去 `tools`，没有就去 `END` | 门口的分流员：要跑腿的去后厨，不用的直接出门 |

几个值得一记的细节：

- **模型节点要“剥皮”**：节点收到的输入是整个 State，所以模型调用通常包在一个函数里，只把 `state["messages"]` 喂给模型（如上面第 1 步）；直接把模型实例塞给 `add_node` 会因为“收到 dict”而报错。
- **`tools_condition` 返回的是 `"tools"` 或 `END`**，所以节点名必须叫 `tools`（或者用路径表改映射）。在 16 节的旅行助手里，每个子助理都有自己定制的路由函数，本质就是 `tools_condition` 的加强版。
- **`MessagesState`** 是 LangGraph 预置的“只有 messages 一个字段”的状态类，内置了 `add_messages` reducer，写小 demo 时连 State 都不用自己定义。

## 3. 容错封装：工具报错别让图崩掉

16 节项目里 `tools/tool_handler.py` 的 `create_tool_node_with_fallback` 就是给 `ToolNode` 加容错的项目级封装，它内部用的是官方机制：

```python
# 方式一：ToolNode 自带 handle_tool_errors 参数（默认 True）——
# 工具抛异常时不会让整张图崩掉，而是把错误信息包成 ToolMessage 塞回对话，
# 让大模型自己“看到报错、想办法补救”
builder.add_node("tools", ToolNode([search_flights], handle_tool_errors=True))

# 方式二：08 节项目的做法——用 with_fallbacks 挂自定义兜底函数，
# 报错时返回一条统一格式的 ToolMessage（详见 tools/tool_handler.py）
builder.add_node("tools", ToolNode(tools).with_fallbacks([RunnableLambda(handle_tool_error)]))
```

**生活化比喻：** 普通助理遇到“查不到航班”就当场撂挑子（图直接报错终止）；靠谱助理会把“这家查不到”如实回报，专家可以换个说法再问。生产环境**永远建议开容错**——这也是 16 节项目所有工具节点都走 `create_tool_node_with_fallback` 的原因。

## 4. 高层快车道：create_agent + middleware

如果你不想手搓上面的循环，LangChain 1.x 提供了一条高层快车道。**注意**：老教程里的 `create_react_agent` 在 LangGraph v1 中已被弃用，官方改推 LangChain 的 `create_agent`：

```python
from langchain.agents import create_agent

agent = create_agent(
    model="gpt-4o-mini",
    tools=[search_flights],
    system_prompt="你是一个专业机票客服",
)
agent.invoke({"messages": [{"role": "user", "content": "帮我查去东京的航班"}]})
```

一行 `create_agent`，内部自动帮你搭好了本节第 1 小节讲的完整循环图。它还支持 **middleware（中间件）**——像给流水线装“质检摄像头”一样，在模型调用前后、工具执行前后插入自定义逻辑（动态 Prompt、敏感词过滤、工具报错重试等）。

### 那到底该用哪条路？

| 场景 | 推荐 |
| :--- | :--- |
| 标准的单 Agent 工具循环，想最快跑通 | `create_agent` 高层 API |
| 需要精确控制每一步：敏感工具拦截、多助理路由、状态栈（如 16 节项目） | 裸写 `StateGraph` |
| 两者之间：先快车道起步，遇到控制需求再“下沉”到裸图 | 混合路线（官方推荐的心智模型） |

> 💡 **一个判断标准**：当你发现自己在 `create_agent` 外面拼命包逻辑时，就该下沉到 `StateGraph` 了；反过来，16 节那种多助理路由图里的每个“助理节点”，内部其实就是一个标准工具循环——高层与底层是同一件事的两个抽象层级。
