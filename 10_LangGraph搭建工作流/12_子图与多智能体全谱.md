# 12 子图与多智能体全谱

07 节我们用“大堂经理 + 状态栈”搭了 Multi-Agent。但有一个事实要先坦白：16 节的旅行助手其实是把主助理和四个子助理**平铺在一张大图里**（靠 `enter_xxx` / `leave_skill` 节点和 `dialog_state` 栈模拟“进出部门”），并不是官方定义的真正**子图（Subgraph）**。这一节讲清真子图怎么建、什么场景值得用，再把官方的多智能体编队模式一次配齐。

## 1. 真子图：图中有图

**生活化比喻：** 平铺大图像一张贴满全公司工位的平面图——所有部门的电话、工位、门牌都在一张纸上，人多了一眼花。真子图像**组织架构图**：总公司只画到“部门”这一级，每个部门内部有自己的小流程图，公司层面只关心“找哪个部门、结果如何”。

子图就是一个**独立编译的图**，直接作为父图的一个节点：

```python
# 1. 先造一个独立的子图（它有自己的 State 和完整内部连线）
flight_builder = StateGraph(FlightState)
# ... add_node / add_edge ...
flight_graph = flight_builder.compile()          # 先编译！

# 2. 再把它整个塞进父图当一个节点
parent_builder = StateGraph(ParentState)
parent_builder.add_node("flight_department", flight_graph)   # 编译后的图 = 节点
parent_builder.add_edge(START, "flight_department")
parent_graph = parent_builder.compile()
```

父子图协作的两条规矩：

- **共享状态键**：父图与子图的 State 如果有同名字段（如 `messages`），数据会自动透传；父图里没有的键在子图内部自成小灶，互不打扰——这正是“部门自治”的价值。
- **跨层导航用 `Command`**：子图节点想直接跳回父图的某个节点（而不是原路返回），用 `Command(goto=..., graph=Command.PARENT)`。

> 💡 **平铺 vs 子图怎么选？** 子图的价值在于**封装与复用**：航班助理要独立测试、要给另一个项目复用、内部状态想对外隐藏——就拆成子图；几十个节点的小项目平铺更直观。05 节提过 `get_graph(xray=True)` 就是用来透视子图内部的。

## 2. 官方多智能体编队全谱

LangGraph 官方把多智能体架构整理成几种标准编队。用“公司组织形态”来比喻：

| 编队 | 谁指挥谁 | 生活化比喻 | 典型实现 |
| :--- | :--- | :--- | :--- |
| **Network（网络型）** | 没有老板，谁都能把任务递给谁 | 小微创业团队，全员互甩协作 | 各 Agent 的工具集里放其他 Agent 的转交工具 |
| **Supervisor（主管型）** | 一个主管专职分派，专家们各管一摊 | 前台大堂经理 + 专员 | 07/16 节的架构（主管用转交“工具”委派） |
| **Supervisor (tool-calling)** | 主管把“呼叫专家”当普通工具用 | 经理直接拨专家的分机号 | 专家被封装成 `@tool` 供主管调用 |
| **Hierarchical（分层型）** | 主管管小组长，小组长管组员 | 总监 → 组长 → 组员，层层汇报 | Supervisor 的递归嵌套 |
| **Handoffs（接力型）** | 两个 Agent 之间直接交接控制权 | 客服工单转接：A 接不了转 B | handoff 工具 + `Command(goto=...)` |
| **Custom（自定义）** | 自由组合 | 混合所有制 | 自绘 StateGraph |

两个最容易混的概念，值得单独掰扯：

- **Handoff 作为“工具调用” vs Handoff 本身就是工具**：前者是 Supervisor 架构的实现技巧（主管调用一个名为 ToFlightAssistant 的假工具，路由函数读它去跳转，即 07 节的做法）；后者强调交接动作本身——交接时通常还会**转移对话上下文或修改状态**，像转接电话时先跟同事交代两句背景。
- **Supervisor vs Network**：主管型可控、好排错，但主管可能成为瓶颈；网络型灵活、无单点，但容易“传话传歪”。生产系统九成从 Supervisor 起步。

## 3. 别重复造轮子：官方现成编队库

| 库 | 给你什么 |
| :--- | :--- |
| [langgraph-supervisor](https://github.com/langchain-ai/langgraph-supervisor) | 一行创建主管 + 专家编队，自动生成转交工具 |
| [langgraph-swarm](https://github.com/langchain-ai/langgraph-swarm) | 一行创建 Swarm（接力式）多智能体，基于 handoffs |
| [langchain-mcp-adapters](https://github.com/langchain-ai/langchain-mcp-adapters) | 把 MCP 服务器上的工具一键挂给 Agent（外部工具生态接入） |
| [agentevals](https://github.com/langchain-ai/agentevals) | 多智能体轨迹评测：对比实际执行轨迹与期望轨迹 |

学这些编队模式不是为了背名字，而是为了**识别问题形态**：需求是“一个总入口、多个专家”→ Supervisor；“专家之间需要互相踢皮球”→ Network / Swarm；“团队大到一层管不动”→ Hierarchical。
