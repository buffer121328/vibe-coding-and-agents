# 12 子图与多智能体全谱

07 节先用“大堂经理 + 状态栈”演示了控制权交接。16 节的旅行助手采用混合结构：机票、酒店和游览助理平铺在父图里，租车助理与并行比价则是真子图。下面先讲清子图，再按当前官方分类重新认识多智能体。

## 1. 真子图：图中有图

**生活化比喻：** 平铺大图像一张贴满全公司工位的平面图——所有部门的电话、工位、门牌都在一张纸上，人多了一眼花。真子图像**组织架构图**：总公司只画到“部门”这一级，每个部门内部有自己的小流程图，公司层面只关心“找哪个部门、结果如何”。

子图就是一个**独立编译的图**，直接作为父图的一个节点：

```python
# 1. 先造一个独立的子图（它有自己的 State 和完整内部连线）
flight_builder = StateGraph(FlightState)
# ... add_node / add_edge ...
flight_graph = flight_builder.compile()          # 先编译！

# 2. 再把它整个塞进父图当一个节点
parent_builder = StateGraph(ParentState)
parent_builder.add_node("flight_department", flight_graph)   # 编译后的图 = 节点
parent_builder.add_edge(START, "flight_department")
parent_graph = parent_builder.compile()
```

父子图协作的两条规矩：

- **共享状态键**：父图与子图的 State 如果有同名字段（如 `messages`），数据会自动透传；父图里没有的键在子图内部自成小灶，互不打扰——这正是“部门自治”的价值。
- **跨层导航用 `Command`**：子图节点想直接跳回父图的某个节点（而不是原路返回），用 `Command(goto=..., graph=Command.PARENT)`。

> 💡 **平铺 vs 子图怎么选？** 子图的价值在于**封装与复用**：航班助理要独立测试、要给另一个项目复用、内部状态想对外隐藏——就拆成子图；几十个节点的小项目平铺更直观。05 节提过 `get_graph(xray=True)` 就是用来透视子图内部的。

## 2. 三个重点实现：放回当前官方分类里理解

配套 demo 仍保留三张可运行图，但它们不是三种互相平级的“官方编队”：Router 是官方模式，Supervisor 应放到 Subagents 下理解，Planner-Executor-Reviewer 则是用 LangGraph 画出的 Custom workflow。

### 2.1 Router 路由分流：医院分诊台

**生活化比喻：** 医院分诊台。病人先到分诊台，护士问两句就分流："发烧去内科、摔伤去骨科、牙疼去口腔科"。分诊台自己不看病，只负责把人送到对的地方。

**适用场景：** 需求类型清楚、各分支互不重叠。它是三种范式里最便宜、最可控的——一次廉价分类调用，就能把 80% 的流量分给轻量分支。

```text
              ┌-> SQL 专员
用户 -> 分诊台 ├-> RAG 专员
              └-> Code 专员
```

### 2.2 Subagents（Supervisor）：主 Agent 调用专家

**生活化比喻：** 项目经理（Supervisor）接下"写一份行业报告"的活，先把需求拆开：一份给调研专员、一份给写作专员。专员干完活交回经理，经理再派下一单，直到全员完工，经理把所有产出汇总成报告交差。**专员之间从不直接对话，所有沟通都过经理的手。**

**适用场景：** 任务需要拆分，专家各有独立 Prompt、工具和上下文窗口，而且专家不需要长期直接接待用户。当前官方推荐的基本实现是：把每个子 Agent 包成一个工具，主 Agent 决定调用谁、给多少上下文、如何汇总结果。

```text
              ┌-> 调研专员 ─┐
用户 -> 主管 ├-> 写作专员 ─┼-> 主管 -> 汇总 -> 最终报告
              └-> ……      ─┘
```

### 2.3 Custom workflow：Planner-Executor-Reviewer 改稿流

**生活化比喻：** 出书三部曲：编辑（Planner）先定大纲，写手（Executor）照大纲写稿，主编（Reviewer）审稿——不满意就带着批注打回重写，直到通过才付印。注意主编手里必须有"最多改 N 版"的死规矩，否则写手会被无限打回。

**适用场景：** 对质量有硬要求、允许重试的场合（代码生成、报告撰写、数据处理管线）。Reviewer 的"打回重做"就是一条显式的**循环边**——这正是 LangGraph 相比"只能单向流水线"框架的核心优势：控制逻辑写在图里，不用全塞进 Prompt。

```text
需求 -> Planner 规划 -> Executor 执行 -> Reviewer 评审
                          ↑                 │
                          └── needs_fix ────┘
                                            │ pass
                                            v
                                          交付
```

### 2.4 Handoffs 与 Skills：另外两条主线

配套工作台没有再复制两张大图，但选型时必须认识它们：

- **Handoffs（接力）**：当前活跃 Agent 会写入状态并把控制权交给另一个 Agent。像客服转接，接手者直接继续和用户对话，适合分阶段、多轮对话流程；
- **Skills（技能包）**：仍由一个 Agent 接待用户，只在需要时加载某个领域的提示词与知识。像医生留在同一诊室，遇到眼科问题才翻开眼科手册；领域多但工具不复杂时，比再造一群 Agent 更省上下文；
- **并行多 Agent**通常落在 Router 或 Subagents 内，通过一次多工具调用或 `Send` 并发执行，不必另造一个编队名字。

## 3. 当前官方五种模式

当前 LangChain 多智能体文档以五种模式组织内容：

| 模式 | 控制权怎么走 | 生活化比喻 | 适合场景 |
| :--- | :--- | :--- | :--- |
| **Subagents** | 主 Agent 把专家当工具调用，结果回到主 Agent | 项目经理打专家分机 | 多领域、要上下文隔离、专家不直接长期接客 |
| **Handoffs** | 工具修改活跃 Agent / 状态，控制权交给接手者 | 客服工单转接 | 分阶段、多轮、接手者需要直接和用户交流 |
| **Skills** | 单 Agent 按需加载专业提示词和知识 | 一个医生按病种翻专业手册 | 专业知识多，但没必要维护多个独立 Agent |
| **Router** | 分类后派给零个、一个或多个专家，再统一合成 | 医院分诊台 | 输入类别清楚、适合并行查询多个垂直领域 |
| **Custom workflow** | 程序员用 LangGraph 明确画节点、循环和并行 | 自建流水线 | 需要确定性步骤、复杂拓扑或混合多种模式 |

07/16 节的“状态栈 + 转交工具”在用户体验上更接近 **Handoffs**：某个专业助理会成为当前活跃角色并直接继续对话；12b 的主管循环图则是在教学层面展示 **Subagents/Supervisor** 的集中调度。不要只看“都用了转交工具”就把两者混成同一种架构。

### 上下文工程：多智能体真正难的不是画箭头

**生活化比喻：** 经理派活时，不会把公司十年的所有聊天记录整车倒给专家，也不会只说“你看着办”。每次交接至少要回答三个问题：

1. **专家为什么会被选中**：工具名和描述是否把能力边界写清；
2. **专家收到什么**：原始用户问题、筛选后的消息、结构化状态，还是一段摘要；
3. **专家交回什么**：完整消息历史、最终答案，还是给主管的一份短报告。

传得太少，专家缺背景；传得太多，Token 暴涨、隐私外泄、工具调用历史还可能配对失败。当前官方文档把这件事称为 context engineering，它往往比“选哪种编队名字”更影响质量。

## 4. 生态库怎么用：先看维护者建议

| 库 | 给你什么 |
| :--- | :--- |
| [langgraph-supervisor-py](https://github.com/langchain-ai/langgraph-supervisor-py) | 兼容已有 Supervisor 项目；维护者目前建议多数新项目直接用“子 Agent 作为工具”的手写模式，以便控制上下文 |
| [langgraph-swarm-py](https://github.com/langchain-ai/langgraph-swarm-py) | Handoffs / Swarm 风格的参考实现；适合需要 Agent 之间接力的场景 |
| [langchain-mcp-adapters](https://github.com/langchain-ai/langchain-mcp-adapters) | 把 MCP 服务器上的工具一键挂给 Agent（外部工具生态接入） |
| [agentevals](https://github.com/langchain-ai/agentevals) | 多智能体轨迹评测：对比实际执行轨迹与期望轨迹 |

现成库能少写样板代码，却不会替你解决上下文裁剪、权限边界、工具回执配对和评测。新项目先按官方五种模式选型，只有库确实匹配需求时再引入。
