# 11 持久执行与容错：崩溃复活与自动重试

长流程跑一半，最怕什么？程序崩了、第三方接口超时了、机器重启了。普通程序只能从头再来——前面烧掉的 Token 和时间全部作废。LangGraph 的 **Durable Execution（持久执行）** 把长流程变成“可以断点续跑的工程”：**只要挂了 Checkpointer，节点执行完的那一刻进度就落袋为安，崩了就从最近一个快照复活。**

## 1. 断点续跑的原理：一步一存档

**生活化比喻：** 爬雪山时每隔一段就打一根冰锥拴上安全绳。滑坠了（程序崩溃），你不会掉回山脚，只会挂在最后一根冰锥上——抖抖雪，接着爬。Checkpointer 就是那些冰锥：**每跨过一个节点，快照自动保存**。

这带来一个反直觉但极其有用的编程模型：你可以把“重启后从断点继续”当成默认能力来设计长任务：

```python
from langgraph.checkpoint.memory import MemorySaver   # 生产换 SqliteSaver/PostgresSaver

graph = builder.compile(checkpointer=MemorySaver())
config = {"configurable": {"thread_id": "order_1001"}}

try:
    graph.invoke(inputs, config)
except Exception:
    # 程序恢复后：同一 thread_id 再次 invoke，
    # 图会自动从最后一个成功节点的快照继续，已完成的节点绝不重跑
    graph.invoke(None, config)
```

两个关键细节：

1. **恢复粒度是“节点”**：半路上没跑完的那个节点会**整个重跑**。所以官方反复强调——节点内部的重活（网络请求、写库）要尽量做到**幂等**（重复执行一次与执行多次结果相同），比如写入用 upsert，扣款先查状态。
2. **`MemorySaver` 只存在内存里**：进程一崩内存就没了。想让“断点续跑”真的抗重启，生产环境必须换 `SqliteSaver` 或 `PostgresSaver` 这类落盘实现——冰锥要打进岩石里，不能打进雪里。

## 2. RetryPolicy：给易碎节点装“安全气囊”

网络抖动、限流 429、偶发超时……这些**瞬时故障**不该让整个流程报废。LangGraph 内置了 `RetryPolicy`，往 `add_node` 上一挂即可：

```python
from langgraph.types import RetryPolicy

builder.add_node(
    "call_flight_api",
    call_flight_api_node,
    retry_policy=RetryPolicy(
        max_attempts=3,                            # 最多试 3 次（含第一次）
        initial_interval=0.5,                      # 首次重试前等 0.5 秒
        backoff_factor=2.0,                        # 指数退避：0.5s、1s、2s……
        retry_on=(TimeoutError, ConnectionError),  # 只对这两类异常重试
    ),
)
```

**生活化比喻：** 打客服热线没接通，隔一会儿再拨——而且越打间隔越长（指数退避），别在一秒钟内狂拨 20 次把对方线路打爆。注意 `retry_on` 要精确：`RetryPolicy` 默认会跳过 `ValueError`、`TypeError` 这类“重试也没用”的编程错误，只对瞬时故障出手；把参数写错放进重试名单是自欺欺人。

## 3. 超时与缓存：省钱省时的两道保险

- **超时**：LangGraph 1.x 支持给节点直接声明 `timeout` 参数（超时即按异常处理，可与重试叠加）；节点内部的 HTTP 调用也建议设置客户端级 `timeout`，防止单个下游接口把整张图拖死。
- **缓存**：LangGraph 1.x 支持节点级缓存——相同输入的节点（尤其是昂贵的 LLM 调用）直接复用上次结果。编译时挂一个缓存实现，节点上声明策略：

```python
from langgraph.cache.memory import InMemoryCache
from langgraph.types import CachePolicy

graph = builder.compile(cache=InMemoryCache())

builder.add_node("expensive_llm_node", node_fn, cache_policy=CachePolicy(ttl=120))
```

**生活化比喻：** 连锁奶茶店的“单子reuse”——同一杯“三分糖去冰珍珠奶茶”配方固定，第一个人点了，后面的直接照方抓料，不用重新研发。缓存适合“输入确定、输出可复用”的节点；带随机性或时效性的结果（实时报价）千万别缓存。

## 4. 容错组合拳：一张清单带走

| 手段 | 防什么 | 关键配置 |
| :--- | :--- | :--- |
| Checkpointer 落盘 | 程序崩溃、机器重启 | `SqliteSaver` / `PostgresSaver` |
| 节点幂等 | 恢复后重跑造成重复副作用 | upsert 写入、先查再改 |
| RetryPolicy | 瞬时网络故障、限流 | `max_attempts` + `retry_on` + 指数退避 |
| 超时 | 下游接口拖死全图 | HTTP 客户端 `timeout` |
| 缓存 | 重复的昂贵调用 | `cache_policy` + TTL |
| `recursion_limit` | 死循环烧钱 | 运行配置 `{"recursion_limit": 25}` |

> 💡 **组合逻辑**：Retry 管“再试一次能不能成”，Checkpointer 管“实在不行下次从哪继续”，缓存管“能不能根本不用试”。三者叠加，才是完整的“跑到一半崩了能续跑”承诺。
